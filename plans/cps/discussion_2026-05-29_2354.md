# Why we're doing CPS this way

**Date:** 2026-05-29 23:54 (local)
**Paired plan:** [plan_2026-05-29_2354.md](plan_2026-05-29_2354.md)

If you've read the plan and you're going "okay but *why* are we doing it like
that?" — this is the file for you. The plan is the recipe. This is the
conversation that produced the recipe.

---

## The thing that started this

TSBeam's emitter, right now, throws an error the moment it sees a `return`
that isn't the last statement of its block. Try to compile something innocent
like:

```typescript
function classify(n: number): number {
  if (n < 0) return -1
  return n * 2
}
```

…and you get yelled at. Mid-block `return` isn't supported.

That's a real problem. Every TypeScript codebase ever written uses early
returns. Guard clauses, null checks, validation — they all look like "if X
then return now, otherwise carry on." If we want TSBeam to be useful, we
have to handle this.

So why is it broken in the first place? Because **TypeScript and Core Erlang
think about programs differently**, and the gap between them is exactly where
`return` lives.

In TypeScript (and JavaScript, C, Python, every mainstream language), a
function body is a *list of statements you execute one after another*. When
you hit `return`, you jump out. Whatever's below doesn't run. The shape of
the function is sequential, and `return` is an escape hatch.

In Core Erlang, a function body is *one expression*. There are no statements,
there's no "next line." Whatever the expression evaluates to, that's what the
function returns. Every branch of every `if` has to produce a value. There's
nowhere to jump *to* — everywhere is already where you're going.

So when we see `return -1` followed by more code, TS says "obviously, the
rest doesn't run." Core Erlang has no way to express "the rest doesn't run."
That's the gap.

## The first instinct: just tell people not to do it

The cheapest fix is to do nothing. Say "TSBeam doesn't support mid-block
return, rewrite your code to thread everything through `if/else` so every
return is at the end of its branch." Done. Zero implementation work.

The problem is people will paste their existing TypeScript and get errors.
They'll close the tab. Adoption dies. We'd be making the language easier on
the compiler at the expense of being unusable.

Killed this option immediately, but worth naming so we don't accidentally
slide back to it.

## The lazy fix: use exceptions as a goto

Here's a clever trick: BEAM has exceptions. We could wrap every function
body in a `try`/`catch`, compile `return X` mid-block as `throw X`, and have
the catch return X. The throw skips the rest. Free early return.

It works. It's ugly.

Two problems. First, BEAM exceptions are *expensive* — they capture stack
traces, walk the call stack, allocate. Using them for control flow is roughly
10x slower than direct function return. If TSBeam programs end up doing a
lot of early-return guard clauses (which they will, because that's how people
write code), we'd be paying for it on every call.

Second, and this matters more: anyone who reads the generated Core Erlang
would spot the trick immediately. It would mark TSBeam as "that hacky thing
that uses exceptions for control flow." The BEAM community is small and
opinionated. We'd be giving up our credibility as a real BEAM compiler in
exchange for saving a couple weeks of implementation work.

Not worth it. Killed.

## The actual fix: rearrange the AST so the problem disappears

Here's the move. Instead of letting the mid-block `return` reach the emitter
and making the emitter handle it, we **rewrite the AST before the emitter
sees it**, in a way that makes every `return` terminal.

Take this:

```typescript
function f(n: number): number {
  if (n < 0) {
    return -1
  }
  return n * 2
}
```

The `return -1` is mid-block. But what is the rest of the block doing? It's
saying "if we didn't return above, do this." That's exactly what an `else`
branch *is*. So we can mechanically rewrite the function to:

```typescript
function f(n: number): number {
  if (n < 0) {
    return -1
  } else {
    return n * 2
  }
}
```

Same behavior, different shape. Now both returns are terminal. The emitter
already knows how to handle this — every branch of the `if` is the value of
that branch. No mid-block return anywhere.

The rewrite is mechanical: "find an `if` whose then-branch ends in `return`,
take everything after the `if` in the same block, make that the synthesized
`else` branch." Recurse if needed (the synthesized `else` might itself
contain another early return).

This trick has a real name in compiler theory: **continuation-passing style
(CPS) lowering**. The "continuation" is "what would have happened next" —
we're making it explicit instead of leaving it implicit. We're not literally
passing functions around; we're materializing the continuation as the
`else` branch of the `if`. Same idea, simpler implementation.

This produces clean Core Erlang. Idiomatic. Fast. The kind of output a BEAM
person would read and nod at. This is the option we're going with.

## "But you said this is half-baked"

This is the part of the conversation where you ask: "wait, this is a real
project, right? Why are we building a subset of CPS instead of just doing the
whole thing now?"

Good question. Pushed back on me hard. The answer is that there's no such
thing as "the whole thing" — and that's not a dodge, it's how compilers
actually work.

CPS isn't a fixed algorithm. It's a *transformation*, and the transformation
is defined per language construct. CPS for arithmetic is trivial. CPS for
`if` is what we just talked about. CPS for `while` with `break` and
`continue` is a different design with different tradeoffs. CPS for
`async`/`await` is the whole reason JavaScript engines are complicated. CPS
for generators is its own animal.

So "full CPS" only means something if you specify "full CPS *for what
language*." Full CPS for TypeScript-the-spec is years of work and involves
every weird corner of the language. Full CPS for what TSBeam currently
accepts — which is `if`, `let`, calls, and arithmetic — *is* the if-rewriting
thing we just described. Those are the same algorithm.

If we built "full CPS for full TypeScript" today, we'd be writing lowering
code for `while`, `try`, `async`, generators — none of which the parser
accepts. The parser would reject those programs before they ever reached our
shiny lowering pass. We'd have written code that does nothing.

Worse than that, we'd be making design decisions about how those constructs
lower to Core Erlang without knowing what the emitter wants. Compiler passes
co-evolve with the language they accept. You can't design lowering for
constructs the emitter doesn't have shape for yet — you'll guess wrong, and
have to redo it when the emitter actually catches up.

The way real compilers work is: **the lowering pass is always complete for
the language the compiler currently accepts.** You extend it every time you
extend the language. There's no point in time where "lowering knows about X
but the parser rejects X" — that would be the actually-half-baked state.

TypeScript itself was built this way. The first version accepted ES3. Each
new TS version added parser + checker + emitter together. There's no
"full TS transformer" file that got written first.

So that's why this plan looks small: it's lowering for the constructs we
have. When we add `while`, there'll be a new plan called something like
`plans/cps/plan_<later-date>.md` for "extend lowering to handle break and
continue inside loops." Each addition is its own file, its own discussion,
its own commit.

## Why split it into one-file-per-construct under `lower/`

When we extend the lowering pass later, we don't want to be editing one giant
`lower.ts` that's grown to 2000 lines. So the architecture from day one is
`src/compiler/lower/` as a directory, with one file per construct that needs
lowering. `lower-early-return.ts` for this plan. `lower-while.ts` later.
`lower-try-catch.ts` later still. `lower/index.ts` composes them.

Cost today: one extra directory and a 5-line `index.ts`. Cost saved: every
future extension is "add a new file" instead of "edit the monolith." That's
the architecture Rust's MIR construction uses. OCaml's lambda pass uses
something similar. It's not a clever trick; it's just what works.

## Why fresh AST instead of mutating in place

The TS Compiler API lets us either mutate nodes in place or use factory
functions (`ts.factory.createIfStatement(...)`) to build new ones.

Mutation is cheaper to write but harder to test. If we mutate, we can't
compare "AST before lowering" to "AST after lowering" — the input is gone.
That makes debugging the lowering pass painful when something weird happens.

Fresh AST means a few more lines of code, but the input is preserved. You
can dump both ASTs, diff them, see exactly what the pass did. When we add
new lowering for new constructs in six months, future-us will thank
present-us for being able to test it.

This is the kind of decision where the cost feels real today and the payoff
is invisible until you need it. We're paying the cost.

## About the `plans/` directory existing at all

There's also a meta-question here: why are we writing planning files at all?
Why not just have the code, the README, and the commits?

Because some decisions don't fit in commits or code. "We rejected
exception-based early return because it would hurt BEAM credibility" isn't
the kind of thing you write in a commit message. It's context. Six months
from now, someone (probably us, possibly an AI agent helping us, possibly a
contributor) will look at the lowering pass and think "wait, why didn't we
just use exceptions, that would have been way easier?" And they'll be right
that it would have been easier. They need to find the conversation where we
talked about it and chose differently.

That conversation is this file. The plan file tells you *what* we're doing.
This file tells you *why* — including what we considered and chose against,
which is often the more useful information.

It also means that when we make a later CPS plan (say, for handling loops),
the discussion file paired with it can say "we're extending the approach
from `discussion_2026-05-29_2354.md` to handle loops" instead of relitigating
everything from scratch. Continuity.

## What this rules out, in plain English

To save future-you (or future-us) from reopening these:

- **No exceptions-as-goto.** We had this conversation. It's slow and it
  looks bad on BEAM. Don't bring it back.
- **No "just don't support early return."** We rejected this for adoption
  reasons. People paste code; the compiler has to accept it.
- **No writing CPS for constructs the parser doesn't have yet.** Orphan code
  is worse than no code. The pass grows with the language.
- **No monolithic `lower.ts`.** One file per construct, always.
- **No mutating the input AST.** Use the factory; preserve the original.

## What's still up in the air

A few things we didn't fully decide and left for the implementation:

- **Early return after a `let`.** Like `const x = ...; if (bad) return; use(x)`.
  The synthesized `else` has to live inside the `let`'s scope, otherwise the
  binding isn't visible. Probably works automatically, possibly needs a tweak.
  We'll find out during implementation.
- **Source positions on synthesized nodes.** When we build fresh AST nodes,
  should they inherit `getStart()`/`getEnd()` from the original code, so
  error messages later point to the right line? Probably yes, but not
  decided.
- **`return;` with no expression.** TypeScript allows it (returning
  `undefined`). TSBeam currently only supports number-typed returns. Do we
  reject `return;` cleanly or silently treat it as `return 0`? Deferred.

## When the next CPS plan gets written

Each new language construct that introduces a way to escape mid-block gets
its own plan + discussion under `plans/cps/`. The triggers are predictable:

- Adding `while`/`for` loops → need to lower `break` and `continue`.
- Adding `try`/`catch`/`throw` → need to handle how exceptions interact with
  `return`.
- Adding `async`/`await` → this is where "full CPS" actually becomes
  load-bearing, because async is fundamentally CPS and there's no shortcut.
- Adding generators / `yield` → coroutines, the hardest case.

When we hit each of those, we make a new plan, have the discussion, and
extend `src/compiler/lower/` with a new file. The architecture we're setting
up today is designed to make each of those a small change, not a refactor.
