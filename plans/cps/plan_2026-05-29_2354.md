# Plan: CPS lowering for early `return` inside `if`

## What this delivers

After this work, TSBeam accepts mid-block `return` inside `if` statements.
The following program, currently rejected by the emitter, will compile and
run on BEAM:

```typescript
function classify(n: number): number {
  if (n < 0) {
    return -1
  }
  if (n === 0) {
    return 0
  }
  return n * 2
}

console.log(classify(-5))   // -1
console.log(classify(0))    // 0
console.log(classify(7))    // 14
```

## Scope

**In scope:**

- Mid-block `return` inside `if` statements (with or without `else`).
- Chained guard clauses (`if A return; if B return; rest`).
- Nested `if` with early returns.
- Early returns after `let`/`const` bindings in the same block.

**Out of scope** (each gets its own plan when the relevant construct lands):

- `return` inside loops (no loops parsed yet).
- `return` inside `try`/`catch` (not parsed yet).
- `async`/`await`, generators.
- `break`, `continue`.
- `return;` with no expression (parser-level decision, deferred).

## Architecture

Add a third pipeline stage: **lowering**.

```text
parse  ─►  lower  ─►  emit  ─►  erlc  ─►  .beam
```

### Files

```text
src/compiler/
  lower/
    index.ts              # exports lower(sourceFile): ts.SourceFile
    lower-early-return.ts # this plan's work
```

`lower/index.ts` composes passes. For this plan it calls just one. Future
plans add `lower-<construct>.ts` files and compose them in `index.ts`.

### Algorithm — `lower-early-return.ts`

For each function body (including the synthesized implicit `main`):

1. Walk the block's statements front-to-back.
2. If the statement is an `if` whose `then` branch ends in `return` and
   there is no `else`:
   - Take all remaining statements after this `if`.
   - Build a fresh `else` branch containing those statements as a block.
   - Recursively lower that synthesized `else` (it may contain more early
     returns or its own `let`s).
   - Replace the original `if` with one that has the new `else`. Stop iterating
     this block — the rest has been consumed.
3. If the statement is an `if` where both branches end in `return`: recurse
   into each branch but leave the surrounding block intact.
4. If the statement is a `Block`: recurse into it.
5. Otherwise: keep the statement unchanged, continue iterating.

The pass must produce a **fresh** `ts.SourceFile` via `ts.factory.*`. Do not
mutate the input AST. Synthesized nodes should inherit source positions from
the original code where possible (`ts.setTextRange`) so future error messages
point to the right line.

### Why the emitter doesn't change

After lowering, every `return` in the AST is the last statement of its
branch. The emitter already handles this case — it terminates the branch's
expression with the returned value. Lowering moves the burden off the
emitter.

## Implementation notes

### Surprise during step 2: the "mid-block return error" doesn't fire

The plan assumed mid-block `return` would surface as the emitter's
`return is only supported as the last statement of a block` error. It
doesn't — the error guard is in `emitNonTerminalStatement` for top-level
`ReturnStatement`s, but mid-block returns are always wrapped in an `if`, so
they go through `emitIf → emitBranch → emitTerminalStatement` and get
emitted as legitimate values of a `case` branch.

The actual bug pattern is **silent value discard**: the `case` produced by
the `if` evaluates to the return value, then that value is discarded by the
outer `do <case> <rest-of-block>` sequencing, so the function always
evaluates to whatever `rest-of-block` produces.

This means the failing test cases produce *wrong output*, not compile
errors. Step 2 verified this:

- `early_return_basic.ts` `f(-3)` printed `-6` (= `-3 * 2`, the fall-through
  path) instead of `-1` (the early-return path).
- `early_return_chain.ts` printed all three `n * 2` values regardless of
  guard conditions.
- `early_return_nested.ts` similarly used the bottom return for all inputs.
- `early_return_else_only.ts` already passed since both branches are
  terminal — no rewrite needed.

The lowering pass still fixes this — by rewriting the mid-block `if + return`
into a terminating `if/else`, the value flows out as the function's actual
return value instead of being discarded. The bug is a symptom of the same
underlying mismatch the plan addresses; it just manifests as wrong output
rather than as the assumed error.

No change to the algorithm or steps. Continuing as planned.

## Open questions to resolve during implementation

- **Fresh AST vs. mutation:** plan says fresh via `ts.factory`. Confirm in
  step 1 whether the API ergonomics push back. If they do, document the
  workaround.
- **Source positions:** plan says synthesized nodes inherit ranges from
  original code. If `ts.setTextRange` is awkward, fine to skip for now and
  open a follow-up. Note the choice here.
- **`else if` chains:** TS represents `if A {} else if B {}` as
  `if A {} else (if B {})`. The algorithm should handle this naturally — the
  `else` is just another `if`. Add a test case if anything weird shows up.
