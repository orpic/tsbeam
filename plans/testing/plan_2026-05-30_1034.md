## What this delivers

After this work, `npm test` is a comprehensive regression check that
covers:

- Every positive fixture (existing 21), with stdout diffed against
  baselines
- Every negative fixture (new), with the compile-time error message
  matched against an expected substring
- Cross-test state isolation (each fixture runs in a fresh process)
- Stderr checked (non-empty stderr on a clean run = failure)
- A meta-test that should fail (validates the harness itself)
- Nine new combination fixtures exercising feature pairs that haven't
  been tested together

Plus:

- `npm run update-baseline` (new) replaces `npm run test:update`.
- A new `errors.ts` introducing `CompileError`; the emitter throws this
  for user-facing compile errors.
- README, AGENTS, CONTRIBUTING updated to reflect the new test contract.

## Architecture

### Directory layout after this work

```text
tests/
  cases/                ← positive fixtures (existing, unchanged)
    <name>.ts
  baselines/            ← stdout snapshots for positive fixtures (existing)
    <name>.out
  rejected/             ← negative fixtures (new)
    <name>.ts           ← input that should fail to compile
    <name>.error        ← expected substring of the compile error
  meta/                 ← harness self-tests (new)
    always_fails.ts
    always_fails.out    ← deliberately wrong baseline
  run.ts                ← updated harness
```

### New error-type infrastructure

```text
src/compiler/
  errors.ts             ← new: CompileError class
  emitter.ts            ← throws CompileError for all user-facing rejections
  lower/...             ← can also throw CompileError as needed
```

`CompileError` is a thin subclass of `Error`:

```typescript
export class CompileError extends Error {
  constructor(message: string) {
    super(message)
    this.name = "CompileError"
  }
}
```

The emitter's existing `throw new Error(...)` calls for *user-facing*
rejections (`.push` is rejected, `arr[i] = x` is rejected, unsupported
expression, etc.) become `throw new CompileError(...)`. Internal
assertion failures (things that should be unreachable, like "BUG: ..."
errors) stay as plain `Error`. This lets the harness distinguish them.

### New runner shape

The harness becomes a small orchestrator:

```text
discoverCases()         → [{ name, kind: 'positive' | 'negative' | 'meta', ... }]
runIsolated(case)       → spawn a child Node process that runs ONE case;
                          returns its structured result
verifyResult(case, r)   → check expected outcome per kind:
                            - positive: stdout == baseline, stderr empty, exit 0
                            - negative: CompileError thrown, message contains expected substring
                            - meta:    expected to fail; runner reports "ok" if it did
```

Each isolated run is a separate `node dist/tests/runOne.js <case-spec>`
invocation. This spawn-per-test is the cost of state isolation. We
batch results in the parent.

A new `tests/runFixture.ts` is the per-case worker:

- Takes a case spec via argv
- Runs the case
- Emits a JSON result to stdout
- Exits 0 (the parent reads the JSON; the case's own pass/fail is in the
  JSON, not the exit code)

The parent `tests/run.ts` orchestrates: spawns workers, collects JSON,
prints the human-readable summary, exits 0 or 1.

### `--update` removed entirely from `tests/run.ts`

`tests/run.ts` no longer accepts `--update`. A new `tests/update.ts`
exists for baseline regeneration:

```text
npm run update-baseline                  # regenerate all positive baselines
npm run update-baseline -- <name>        # regenerate one
```

`update-baseline` does NOT touch `tests/rejected/.error` files —
regenerating those silently is exactly the footgun we're guarding
against. For negative fixtures, the workflow is: edit the `.error` file
by hand when you intentionally change a rejection message.

If we ever need automated `.error` regeneration, that's a separate `npm
run update-error` script. Not in this round.

### Failure-message hint

When `npm test` reports failures (any kind), the summary line includes:

```text
3 passed, 1 failed (4 total)

If a positive-test failure reflects an intentional change, run:
  npm run update-baseline
For negative-test failures, edit the .error file by hand.
```

Single hint, both cases covered.

### Step 2: refactor the harness into orchestrator + worker

## Implementation notes

Went through all seven steps; took two real diversions that the plan
didn't fully anticipate. Final state: 37 fixtures passing (21 original
positive + 6 negative + 1 meta + 9 combination).

1. **`moduleFunctions` set → map.** The plan had this as part of step 1
   (typed errors), but it actually surfaced in step 6 when
   `combo_map_named_function.ts` failed with `erlc` rejecting the output.
   The fix required knowing the arity of each module function (not just
   its name) so we could emit a fname reference (`'double'/1`) when the
   name appears as a value. Changed `Set<string>` to
   `Map<string, number>` in the emitter. Two callers updated; no
   behavior change for existing fixtures.

2. **Core Erlang fname-as-value syntax surprise.** First attempt emitted
   `fun 'double'/1` (Erlang-style). Core Erlang rejected it. Correct
   syntax at this level is bare `'name'/arity` — no `fun` keyword.
   Verified in `local_sandbox/fun_ref.core` before fixing.

3. **`typeof` had to be added.** Wasn't in scope per the plan, but
   `combo_mixed_filter.ts` used `typeof x === "number"` as its filter
   predicate (idiomatic TS for "is this a number?"). Per the no-deferring
   rule, added `typeof` to the emitter. Lowers to a Core Erlang `case`
   expression with type-tag guards (`is_integer`, `is_float`,
   `is_boolean`, `is_list`, `is_tuple`). Returns one of `"number"`,
   `"boolean"`, `"string"`, `"object"`. Note: today's strings are still
   char lists, so `typeof "hi"` returns `"string"` via the `is_list`
   branch. Once Phase 2 step 4 (strings as binaries) lands, the
   `is_binary` branch becomes the primary string check.

4. **Per-process isolation cost.** ~14 seconds total for 37 fixtures
   (~380ms per fixture). The plan budgeted 5-10s. Real-world bound is
   actually fine — most of the time is `tsc` warming up in each child.
   If we cross 60s we'll consider a fast-path mode, but for now it's
   acceptable.

5. **The meta-test caught itself.** When I first wrote it, I had the
   logic inverted ("pass if matches"). The runner reported the meta
   fixture as failed, which told me the harness was working as designed
   — the meta-test would have caught a real harness bug.

6. **Stderr-must-be-empty surfaced nothing.** All 21 existing positive
   fixtures pass with empty stderr, which is good — means no benign-but-
   noisy warnings hiding in our generated code. Earlier we'd seen
   "no_file: Warning..." from erlc on the pre-CPS-lowering versions of
   `early_return_chain` and `early_return_nested`; those went away when
   lowering started producing proper case expressions instead of
   discarding values via `do`. So this check effectively validates the
   CPS pass keeps the code warning-free.

7. **Did NOT add `--update` warning for negative/meta.** Plan said
   "soft warning" — that warning only fires when no filter is set, to
   keep `npm run update-baseline -- some_case` clean. Minor polish; not
   a behavioral issue.

No deviation from final scope. Each combo fixture either passed
immediately (revealing nothing) or surfaced exactly one bug fixable
inline. No `.skip.ts` escape hatches used.

## Open questions to resolve during implementation

1. **Total runtime.** 21+6+1+9 = 37 fixtures, each in its own child
   process. Estimated runtime: 5-10 seconds. If it exceeds 30s, consider
   parallelization (run children concurrently with a worker pool). Not
   premature optimization — actual user-facing wait.

2. **Error message matching: substring vs regex.** Plan says substring.
   If a future error message becomes order-dependent or has runtime
   identifiers (file paths, line numbers), we may want regex. Add then,
   not now.

3. **Combination fixtures that fail due to real bugs.** Fix them in this
   round — no deferring. If a bug looks genuinely multi-day, stop and
   flag for discussion before continuing. The round isn't done until all
   nine combination fixtures pass.

4. **`tests/runFixture.ts` startup overhead.** Each child needs `tsc`'s
   output already built. We rely on the top-level `npm test`'s
   `tsc && ...` running first. Workers shouldn't re-tsc. Verify in step 2.

5. **Naming the per-worker file.** `runFixture.ts` is clear but uninspiring.
   Alternatives: `worker.ts`, `runner-child.ts`. Defer; stick with
   `runFixture.ts` unless it gets confusing in practice.
