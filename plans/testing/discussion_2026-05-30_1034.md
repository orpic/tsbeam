# Why we're hardening regression coverage now, and how

**Date:** 2026-05-30 10:34 (local)
**Paired plan:** [plan_2026-05-30_1034.md](plan_2026-05-30_1034.md)

If you've read the plan and you're wondering why a "just write more tests"
step needed this much design — read on.

---

## The moment that triggered this

After Phase 2 step 2 shipped (arrow functions + array methods), we had 21
fixtures passing on BEAM. All green. Felt great. Then the question landed:

> "Are we adding tests comprehensively so we don't regress?"

The honest answer was no — we had positive-path coverage and nothing else.
Every fixture asserted "this program produced this output." Nothing
asserted "this program was correctly rejected." Nothing combined two
features and watched them interact. Nothing checked the error message
wording. Nothing isolated tests from each other to detect cross-test
state leaks.

The CPS implementation almost had a state leak (the `moduleFunctions`
set wasn't being cleared between modules — caught it because step 2
forced me to introduce that set, not because tests caught it). A different
emitter regression could just as easily slip through.

So the work this plan is doing isn't "add more tests." It's "stop the
class of bugs we currently can't see."

---

## The full inventory of gaps we found

When we sat down to enumerate, there were 13 different ways the harness
could miss a regression. The user picked everything except a few low-value
items (compiler-output snapshots, CLI tests, naming-convention lint).
That leaves a focused list:

| # | Gap                                       | Why it matters                                      |
| - | ----------------------------------------- | --------------------------------------------------- |
| 1 | Negative paths not automated              | Today's rejection messages only get manual checks  |
| 2 | Feature combinations not exercised        | Real bugs hide at the boundaries                   |
| 3 | Error-message wording not asserted        | "It rejected" isn't enough; *how* it rejected matters |
| 4 | Compiler errors aren't typed              | Harness can't distinguish reject vs runtime crash  |
| 7 | No cross-test isolation                   | State leaks pass alone, fail in suite               |
| 8 | Stderr ignored on pass                    | We've already seen real warnings going unnoticed   |
| 9 | No test for the harness itself            | If the harness lies, nothing tells us               |

Plus three "quality, not correctness" gaps deferred to a later round:

- **#5** snapshot generated Core Erlang (catches "still runs but is now slow")
- **#6** detect when generated output changed without behavior changing
- **#10** human-in-the-loop sanity check on baseline updates
- **#11** snapshot the lowered AST per pass

Deferred because they're about *quality regressions*, not *correctness
regressions*. A pipeline that got 10% slower is a real issue but not the
same kind of issue as a function that returns the wrong value.

## The hardest design call: one command or two?

The original setup had `npm test` (strict) and `npm run test:update`
(regenerate baselines). Two commands. Two mental models. The user pushed
back: "having multiple test scripts will confuse us later."

The temptation was to fold update behavior into `npm test` itself —
"`npm test` does everything by default." But that hides a footgun: if
update is the default, then any regression becomes the new expected
behavior the moment you run the command. The whole point of baselines
disappears.

The next try was a flag — `npm test -- --update`. One command, two modes.
But the user observed something sharper: if `npm test` can update
baselines, the name is misleading. It's not really *testing* in that
mode; it's *recording*. Tools should be named after what they do.

So we landed here:

- **`npm test`** — strict comparison only, never writes anything. Always
  the safe default. CI runs this.
- **`npm run update-baseline`** — regenerates baselines. Separate command.
  Distinct name. No "test" in it.
- The failure message from `npm test` includes a one-line hint:
  `If this change was intentional, run: npm run update-baseline`.

Two scripts, but each one does exactly one thing, and the names match
the actions. Compared to "one command with a flag," this is better
because:

- A new contributor reading `package.json` immediately understands what
  each does. No flag semantics to memorize.
- The CI script is just `npm test`, period. No flags to forget.
- The destructive operation (overwriting baselines) is gated behind a
  command you have to type deliberately. Friction in the right place.
- If we ever add other ergonomics later, they fit cleanly: `npm test --
  arithmetic` filters by name; `npm run update-baseline arithmetic`
  filters baseline updates. Same logic both sides.

The seatbelt stays on, but it's not annoying to put on.

## Why state isolation is default, not opt-in

The user pushed back on my "opt-in via `test:strict`" suggestion:

> "this also pass alone, fail together... ci check everything one test
> command thats enough... having multiple test scripts will confuse us
> later"

Translated: if isolation catches bugs, it should run *every* time. The
alternative (opt-in) is a guarantee that we'll forget to enable it
exactly when it matters — right before a regression ships.

This is the right call. The implementation cost is small:

- Each fixture runs in a child process spawned by the runner.
- The runner aggregates results.
- Total runtime goes up — probably 2-3x because each child pays Node
  startup overhead. For 21 fixtures this is maybe 5 seconds instead of
  2 seconds. Acceptable.

If runtime ever becomes a real problem (200+ fixtures), we can add an
opt-in *fast* mode (`npm test -- --fast`) that batches. But the default
stays isolated.

## Why the meta-test exists

If the harness has a bug — say, the diff function always returns "match"
— every test would pass, including ones that should fail. We'd ship a
broken compiler with a green CI. No way to catch this from inside the
harness itself.

The meta-test is a fixture that's *expected to fail*. Its baseline is
deliberately wrong. The harness runs it like any other test, and the
runner has special logic: "this case should report as FAIL; if it
reports as OK, the harness itself is broken."

It costs ten lines of code and three lines of fixture. Prevents a whole
class of "everything passed but actually nothing was checked" disasters.
No reason not to include it.

## Negative-test design: how do we assert error messages?

This is the most-considered part of the design. The shape we landed on:

```
tests/rejected/<name>.ts        ← input (same as cases/, different dir)
tests/rejected/<name>.error     ← expected error message (substring match)
```

Mirror of `tests/cases/` + `tests/baselines/`. Same harness, different
expected-outcome semantics:

- Positive case: compile + run + compare stdout to baseline.
- Negative case: compile + expect a thrown error + compare its message
  to the `.error` file's content (substring match, not exact — error
  messages can have helpful trailers like file paths that we don't want
  to assert on).

Why substring match instead of exact:
- The error message can legitimately evolve (add a column number, add a
  file path, add a "did you mean...?" hint).
- Exact match would fail on any cosmetic change and force a baseline
  regeneration.
- Substring captures the *meaningful* part: the actual reason for the
  rejection.
- If we ever want stricter matching, we can layer it on (a `.error-exact`
  variant). Don't over-design today.

The `.error` files are checked into the repo. Anyone reading them sees
exactly what each rejection looks like. They're as much documentation as
they are tests.

## Why typed error classes matter (gap 4)

Right now, every error thrown by the emitter is a generic `Error`. The
harness can't tell the difference between:

- "User wrote bad TS, compiler correctly rejected it" (expected for
  negative tests)
- "Compiler bug — internal assertion failed" (unexpected, should crash
  loudly)
- "BEAM runtime error during execution" (different problem entirely)

For negative tests, this matters. We want the harness to be able to say
"I expected a `CompileError` here, got a `RuntimeError` — that's wrong
even though something errored." Generic `Error` can't do that.

Solution: a small `errors.ts` with at minimum a `CompileError` class that
the emitter throws. The harness checks `err instanceof CompileError`
when running rejection tests. Anything else thrown is an unexpected
crash and gets reported differently.

This is a small change — 20-ish lines including the new file. It pays
off whenever we add more error types later (lowering errors, type errors,
runtime errors).

## Feature combinations: what to test

The gap is real but the scope is open-ended. Combinations are infinite.
The pragmatic move: pick the high-value pairs that cross feature boundaries
known to interact:

| Combination                                  | Why it might break                                |
| -------------------------------------------- | ------------------------------------------------- |
| Early return inside arrow body               | CPS lowering runs before emit; arrow bodies are emitted via emitBlock — does CPS lowering reach inside them? |
| Arrow capturing tuple element                | The arrow's body references an outer variable; that variable is `element(I, tup)`. Does the binding work? |
| `.map(f)` where `f` is a named function      | The dispatch in emitCall is `apply 'f'/arity`; does that work when passed to lists:map? (Hint: probably not without a `fun 'f'/1`.) |
| `.filter(p).map(f).reduce(r, 0)` pipeline   | Triple nested method calls; tuple-list-tuple-list-tuple-list-value flow |
| Function declared inside another function    | Inner function references outer parameter — does lexical capture work? |
| Recursion (function calls itself)            | Tail-call optimization — BEAM should handle but we've never tested it |
| Empty array `[]` through methods             | Edge case for fold-style ops |
| Mixed-type array `[1, "a", true]` filtered  | The callback type expectations vs runtime tags |
| Captured `let` shadowed in inner scope       | Does the emitter's `_x` mangling collide? |

Nine combinations chosen. Each becomes a fixture under `tests/cases/`,
named `combo_<feature1>_<feature2>.ts` so the harness picks it up
automatically. If any of them surface a bug, that's exactly the kind of
bug this round was designed to catch.

## What this rules out

- ❌ Auto-updating baselines on failure (Option A). Footgun.
- ❌ A `--update` flag on `npm test`. Bad naming.
- ❌ Opt-in state isolation. Defeats the purpose.
- ❌ Exact-match error message assertions. Too brittle.
- ❌ Per-pass output snapshots (deferred to a later round).
- ❌ Compiler-output structural assertions (gap 5; deferred).
- ❌ Tests for the CLI's argument parsing (gap 12; deferred until CLI
   surface grows).

## What's still open after this round

Three quality-not-correctness gaps deferred:

- **Quality regression detection (gaps 5, 6, 11)** — would require
  snapshotting generated Core Erlang and surfacing diffs. Worth doing
  when the optimizer starts to matter.
- **Baseline sanity validation (gap 10)** — a `npm run update-baseline
  --interactive` mode that diffs before writing. Worth adding the first
  time we accidentally lock in a wrong baseline.

Add a new paired plan under `plans/testing/` when either of those becomes
load-bearing.
