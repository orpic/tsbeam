# Why Phase 3 looks the way it does

**Date:** 2026-05-31 02:54 (local)
**Scope:** Phase 3 (concurrency) overall design direction. Individual
feature plans reference this document.

---

## The reason TSBeam exists

Phase 2 discussion said it plainly:

> **Concurrency (Phase 3). The whole reason TSBeam exists.**

BEAM's defining feature is lightweight processes — millions of them,
preemptively scheduled, crash-isolated, communicating by message
passing. Node.js has exactly one thread and an event loop that
cooperatively multiplexes I/O callbacks. That's TSBeam's pitch: write
the same TypeScript you already know, get real parallelism and fault
isolation for free.

---

## The principle applied to concurrency

The design principle says:

- Positive shocks (faster, more parallel, more robust) are welcome.
- Negative shocks (slower, more confusing) are avoided.
- No hidden shocks — document what's different.

For concurrency this means:

1. **The TS programmer's existing concurrency vocabulary is
   `async`/`await`.** Forcing them to learn `spawn`/`send`/`receive`
   before writing concurrent code is a negative shock — a new mental
   model they didn't sign up for.

2. **BEAM processes are the positive shock.** Each `async` call spawns
   a real BEAM process. You get preemptive scheduling, crash isolation,
   and true parallelism — things Node's `async` can never deliver. The
   syntax is familiar; the runtime is vastly better.

3. **The observable difference must be documented.** On Node, `async`
   is cooperative and single-threaded. On TSBeam, `async` is truly
   parallel. Programs that depend on single-threaded ordering of
   side-effects will behave differently. This is a documented positive
   shock, not a hidden one.

## Options considered

### Option A: async/await mapped to processes (CHOSEN)

TS surface: `async function`, `await expr`.
BEAM target: calling an async function spawns a process; `await` does
a `receive` to collect the result.

Why chosen:
- Familiar TS vocabulary — zero new concepts for the user.
- Maps perfectly to BEAM's strengths — one process per async call
  is exactly what BEAM is built for.
- Follows the principle: no negative shock (same syntax), positive
  shock (real parallelism instead of cooperative scheduling).

### Option B: explicit process API (spawn/send/receive)

TS surface: `spawn(() => ...)`, `send(pid, msg)`, `receive(...)`.
BEAM target: direct `erlang:spawn`, `!`, `receive`.

Why rejected as step 1:
- Requires TS programmers to learn a foreign model (negative shock).
- Not how idiomatic TS expresses concurrency.
- Appropriate as a later "power user" escape hatch (step 2 or 3),
  not as the primary interface.

### Option C: Actor/GenServer classes

TS surface: `class Counter extends Actor { handle(msg) { ... } }`.
BEAM target: GenServer callbacks.

Why ruled out for Phase 3:
- Requires class support, which TSBeam doesn't have yet (Phase 4).
- Higher-level abstraction that should be built on top of the
  primitives, not as the foundation.
- Can't do this without `this`, method dispatch, constructors.

### Option D: coroutines in one process

TS surface: `async`/`await` as syntax sugar, but mapped to CPS within
a single BEAM process (like Node's event loop on BEAM).

Why rejected:
- Loses the entire point of TSBeam. One process with cooperative
  scheduling is what Node already does. No parallelism, no crash
  isolation, no preemptive scheduling.
- Reinvents BEAM's scheduler badly in userspace.
- Zero positive shock. Just Node with extra steps.

## The promise representation

A promise on TSBeam is a `{Ref}` tuple — a one-element tuple holding
a unique BEAM reference. This is the minimal representation:

- The spawned process knows the caller's PID (captured at spawn time
  via `self()`) and the Ref (created before spawn).
- When the async body completes, the spawned process sends
  `{Ref, Result}` to the caller.
- `await` extracts the Ref from the promise tuple and does a
  `receive` matching on `{Ref, Value}`.

Why not just a PID? Because a PID identifies a process, not a
specific computation's result. Multiple awaits on the same process
would be ambiguous. Refs are unique per call — exactly one result
per ref.

Why not `{Pid, Ref}`? The caller doesn't need the spawned PID for
the basic await protocol. Keeping it minimal means the representation
can grow later (add timeout, add monitor ref) without breaking the
core shape.

## Strict unawaited-call rejection

In step 1, calling an async function without `await` is a compile
error. Rationale:

1. **Functional:** every expression's value should be consumed.
   Fire-and-forget is the imperative pattern, not data flow.

2. **TS best practice:** `@typescript-eslint/no-floating-promises`
   is the community standard. Unawaited promises swallow errors and
   create non-deterministic ordering.

3. **Consistency with TSBeam's existing rejections:** we reject
   `.push()` because idiomatic TS uses `[...arr, x]`. Rejecting
   floating promises is the same move — enforce the good pattern,
   reject the sloppy one with a helpful error.

4. **Simpler step 1 semantics:** if every async call is awaited,
   we don't need to reason about orphan processes, unhandled errors
   in background tasks, or process cleanup on main exit.

Later steps can add explicit fire-and-forget via `spawn(() => ...)`
(the Option B escape hatch) for users who genuinely want background
work. That's a deliberate choice, not an accidental omission of
`await`.

## Scope boundary: what Phase 3 is NOT

- Not OTP (supervisors, GenServer, application trees). That's Phase 4.
- Not classes or `this`. Also Phase 4.
- Not `Promise.all` / `Promise.race` in step 1 (step 2 or 3).
- Not error propagation across processes in step 1 (needs `try/catch`
  first, which is its own feature).
- Not channels, not streams, not pub/sub. Higher-level abstractions
  for later.

---

## Build order for Phase 3

1. **Step 1 (this plan): basic async/await.** Async functions, await
   at call sites, process-per-call, strict no-floating-promises.
   Proves the model end-to-end with a working fixture.

2. **Step 2: mid-body await (async CPS lowering).** Allow `await`
   in the middle of an async function body. Requires a lowering pass
   that splits the async body at each `await` point into continuation
   segments.

3. **Step 3: Promise.all / concurrent composition.** `await
   Promise.all([a(), b(), c()])` — spawn N processes, await all
   results. The first real "better than Node" demo: true parallel
   execution of independent async work.

4. **Step 4: explicit spawn (power-user escape hatch).** The
   `spawn`/`send`/`receive` API for users who want raw process
   control. Fire-and-forget becomes legal here.

5. **Step 5: error propagation (linked processes).** When an async
   function throws, the awaiting process gets the error. Requires
   `try/catch` support and BEAM process links/monitors.

## The observable difference from Node (documented, not hidden)

Programs that do this on Node:

```typescript
async function log(msg: string): Promise<void> {
  console.log(msg)
}
await log("first")
await log("second")
```

Will print `first` then `second` on both Node and TSBeam (sequential
awaits are sequential).

But programs that do this:

```typescript
const a = computeA()  // spawns process
const b = computeB()  // spawns process
const result = await a + await b
```

On Node: `computeA` runs to completion, then `computeB` starts.
On TSBeam: both run in parallel (different processes).

This is the positive shock. It's faster. It's what the user probably
wanted. And it's documented. Programs that depend on single-threaded
ordering of side effects in concurrent code are broken on Node too —
they just happen to work by accident because Node is single-threaded.
We don't protect that accident.
