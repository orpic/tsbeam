# Why we're flipping strings to binaries

**Date:** 2026-05-30 15:42 (local)
**Paired plan:** [plan_2026-05-30_1542.md](plan_2026-05-30_1542.md)
**Parent discussion (Phase 2 principle):** [discussion_2026-05-30_0058.md](discussion_2026-05-30_0058.md)

This is step 4 of Phase 2. Orthogonal to steps 3/5/6 (objects, Map/Set,
interfaces) — those are about adding new constructs; this is about
changing how an existing construct emits.

---

## What strings look like today

TS string literals like `"hello"` currently emit Core Erlang strings:
the text `"hello"` in Core Erlang means a list of integer charcodes
`[104, 101, 108, 108, 111]`. That works — `io:format` accepts char
lists — but it has consequences:

- `s.length` would be O(n) (list length traversal)
- `s[i]` would be O(n) (list traversal)
- `s + t` would be O(n) (list append; copies the left side)
- Printing via `~p` shows strings as quoted lists (we've seen this in
  `array_mixed_types` outputting `"two"` with quotes)

Each of these is a negative shock vs TS, which delivers O(1) indexed
access and length. We promised "no negative shocks." The fix is binaries.

---

## What binaries give us

A BEAM binary `<<"hello">>` is a contiguous byte array. The runtime
gives us:

- O(1) `byte_size/1` (length)
- O(1) `binary:at/2` (indexed access by byte)
- O(n+m) concatenation via `<<A/binary, B/binary>>` — same as TS, with
  good constants because BEAM uses iovec under the hood
- Pretty printing via `~p` shows them as `<<"hello">>` (still quoted)
  or via `~s` shows them unquoted as the actual text

Match TS's complexity contract. Better runtime cost than char lists.
This is the "Elixir made the right call here" move — Elixir's strings
are binaries by default; we follow.

---

## The cost of switching

The flip isn't free:

1. **String literal emission changes.** Today `JSON.stringify(expr.text)`
   produces `"hello"` (Core Erlang char list). We need
   `<<"hello"/utf8>>` (Core Erlang binary literal with UTF-8 encoding).
2. **String concatenation changes.** Today `a + b` for strings would
   become `lists:append` (same as list concat). We don't have explicit
   string concat yet — the `+` operator is always integer arithmetic.
   With binaries, we'd need to detect "is this string concatenation?"
   and route to `<<A/binary, B/binary>>`.
3. **`s.length` changes.** Today we have `.length` for arrays only. We
   need to extend property-access dispatch to handle `.length` on
   binaries → `byte_size/1`.
4. **`s[i]` changes.** Today element access is for tuples (arrays).
   Strings would need `binary:at(B, I)` (note: returns the byte, an
   integer — not a single-char string. TS returns a single-char string.
   So `s[i]` would return an int code where TS returns a one-char
   string. Real semantic gap.)
5. **`io:format` changes.** `~p` prints binaries as `<<"hi">>`; we'd
   want `~s` for `console.log` to print plain `hi`. But `~s` requires
   the argument to actually be a string — if we use it for non-strings
   (numbers, booleans), it crashes. So `console.log(x)` needs to dispatch
   on type: strings get `~s`, everything else gets `~p`. Or we keep
   `~p` and accept the `<<"hi">>` printing.

The fifth point is the most annoying. Either:

- **Option A: keep `~p` everywhere.** Strings print as `<<"hello">>`.
  Ugly but consistent.
- **Option B: dispatch on type.** Need to know at *emit time* whether
  the argument is a string. Sometimes possible (literal `"hi"`), often
  not (`console.log(maybeString)`).
- **Option C: emit a runtime helper.** `console.log` lowers to a call
  to our own helper function that does the type dispatch at runtime.
  Adds a runtime function. Most flexible.

**Decision: Option C.** We add a small `tsbeam_io:print` helper that
type-dispatches and uses the right format specifier. This is a real
runtime-library addition — first time we ship code our compiler
*depends on*. Acceptable cost; we'd hit this eventually anyway when
arrays/objects need pretty-printing too.

Actually wait — Option C requires either:

- (a) Inlining the helper in every module that uses `console.log`, OR
- (b) Compiling a separate `tsbeam_io.beam` module and linking against it.

(a) is bloat. (b) is the start of a real runtime/stdlib that TSBeam
programs depend on at runtime.

**Decision: defer the print-formatting cleanup to its own future plan.**
For this round, we ship strings-as-binaries but keep `console.log`
using `~p`. That means string output will show `<<"hello">>` in the
short term. Ugly, documented, fixable later when the runtime story
becomes a real conversation.

In other words: this step is about making `s.length`, `s[i]`, and
`s + t` work correctly with O(1) / O(n+m) complexity. The printing
side is a separate problem we acknowledge but don't fix here.

## The `s[i]` semantic gap

TS `"hello"[1]` returns `"e"` (a single-char string). BEAM
`binary:at(<<"hello">>, 1)` returns `101` (the byte code for 'e').

We can match TS by extracting a 1-byte binary instead:
`binary:part(B, I, 1)` returns `<<"e">>`. Slightly slower than
`binary:at` (allocates a new binary) but matches semantics.

**Decision: use `binary:part` for `s[i]`** so the return type matches
TS expectations. The O(1) promise still holds.

---

## Detecting string operations

Several places need to know "this is a string, not a number/array":

- `a + b` — string concat vs integer add
- `a.length` — `byte_size` vs `tuple_size`
- `a[i]` — `binary:part` vs `element`

Options:

**Option A: use the TypeScript type checker.** Same approach as
interfaces — consult `program.getTypeChecker()` for the type of each
expression. If it's `string`, route to string operations.

**Option B: emit type-dispatched code.** Every `a + b` becomes:
```
case {is_binary(A), is_binary(B)} of
  {true, true} -> <<A/binary, B/binary>>
  _ -> A + B (integer add)
end
```
Works at runtime but bloats output massively.

**Option C: heuristics.** Look at literal types — `"hello" + x` is
clearly string concat. But `f() + g()` is ambiguous without types.

**Decision: Option A.** The interfaces work already needs the type
checker; we extend its use here. Cost is small once the type-checker
infrastructure is in place from step 3.

This means **steps 3-6 should land before step 4 in implementation
order**, even though strings are conceptually orthogonal. The type
checker integration is the shared dependency.

Updating order: **objects/Map/interfaces first, strings last.**

---

## What this rules out

- ❌ Char-list strings as the BEAM representation. Done with that.
- ❌ Mixed representation (some strings binaries, some lists). One
  representation; consistency.
- ❌ Runtime type dispatch for every operation (Option B above). Bloat.
- ❌ Fixing the `console.log` format-string issue in this step.
  Acknowledged, deferred.

## Still open

- The print-formatting story. We need `tsbeam_io:print` (or inlined
  type-dispatch) eventually. Probably a Phase 3 cleanup; we don't
  block this step on it.
- Template literals (`` `hello ${name}` ``). Surface-level lowering
  to `<<"hello", Name/binary>>`. Add later as a thin extension; not
  in this step.
- Unicode considerations. BEAM binaries are byte arrays. UTF-8 in /
  UTF-8 out works fine for printing; indexed access by byte vs
  character is a real semantic difference. TS treats strings as UTF-16
  code units; we'd be byte-indexed. For ASCII this doesn't matter; for
  multi-byte chars it does. Defer the discussion.
