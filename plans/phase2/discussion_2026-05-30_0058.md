# Why Phase 2 looks the way it does

**Date:** 2026-05-30 00:58 (local)
**Scope:** This discussion covers Phase 2 (type system + data structures) as
a whole. Individual feature plans under `plans/phase2/` reference this
document instead of re-arguing the principle.

If you've read the plan files and you're going "okay but *why* are arrays
tuples and not lists?" — this is the file for you.

---

## The principle that drives every Phase 2 decision

The TypeScript programmer who writes code that runs on TSBeam should
**never have a worse experience than they had on Node.** Things that are
fast in TS should be fast in TSBeam. Things that are slow in TS are allowed
to be slow in TSBeam. Things that are fast on BEAM but slow in TS are
**free upgrades** that we lean into — TS programmers don't complain when
their code gets faster.

Phrased more carefully:

- **Positive shocks (faster, more parallel, more robust) are welcome.**
  We don't artificially hold ourselves back to match TS's worse choices.
- **Negative shocks (slower than equivalent TS) are what we avoid.** When
  BEAM genuinely can't match a TS complexity guarantee, we pick the closest
  alternative and document it.
- **"No shock" is not "be brittle as a baked biscuit."** If BEAM gives us a
  big-integer type for free, TS programmers get arbitrary-precision
  integers. We don't downgrade to match TS's 64-bit float just for
  symmetry.

This is the principle. Every concrete Phase 2 decision is derived from it.

---

## Idiomatic TS makes the principle easier to keep

Modern TS is **functionally written**. The conventions are:

- `arr.map(f)` instead of mutating loops
- `arr.filter(p)` instead of conditional push
- `[...arr, x]` instead of `arr.push(x)` when mutation isn't wanted
- `{ ...obj, field: x }` instead of `obj.field = x`
- `const`, not `let`, by default
- Pure functions, immutable updates, returning new structures

Why this matters for us: **idiomatic TS already avoids the operations BEAM
is slow at.** The TS programmer who writes a tight `arr[i] = x` loop is
doing something that even other TS programmers would code-review against.
That's not the audience we have to optimize for. The audience we *do* have
to optimize for is the one writing `users.filter(u => u.active).map(u =>
u.name)` — and on BEAM, that's a `lists:filter ∘ lists:map` chain, which is
fast.

So when we pick "tuples for arrays, accept O(n) push," we're not making the
common case slow. The common case (functional pipelines) doesn't push. The
case we're pessimizing (index-assignment in a loop) is rare *and*
non-idiomatic *and* easy to spot in a code review.

This is a happy accident: TS culture has already done half the work of
mapping to BEAM cleanly. We're just following the road.

## What BEAM is genuinely better at

These get documented as positive shocks, not hidden:

- **Arbitrary-precision integers.** TS `number` is a 64-bit float and loses
  precision above 2^53. BEAM integers are arbitrary precision. `2n ** 100n`
  works without `BigInt` ceremony — `2 ** 100` just works.
- **Tail-call optimization.** Recursive code that stack-overflows on Node
  runs forever on BEAM.
- **Immutability by default.** Most modern TS is already written this way
  by convention. We deliver it as a runtime guarantee — no aliasing bugs
  from shared references.
- **Native pattern matching.** `const [a, b] = arr` is a free O(1) match
  on tuples, not a heap allocation.
- **Concurrency (Phase 3).** The whole reason TSBeam exists.

These don't need apologies in the README. They're features.

## What BEAM is genuinely worse at, and what we do about it

The honest list of gaps, in priority order:

### Gap 1: No O(1) hashmap

TS `Map<K,V>.get(k)` is O(1) average. BEAM map lookup is O(log n) (HAMT —
hash array mapped trie). Same shape but different complexity.

**Could we fix it?** Only by writing our own hashmap in BEAM. Our handwritten
BEAM-level hashmap would be slower in *absolute* terms than OTP's HAMT
implemented in C inside BEAM. We'd improve asymptotic complexity and
degrade real-world performance. Bad trade.

**What we do:** BEAM map. Document that `Map<K,V>` is O(log n) average, not
O(1). For typical sizes (up to ~10k entries), log₂ is ~13 — a small
constant. WhatsApp runs on this. So can TS code.

### Gap 2: No O(1)-access mutable array

TS `Array<T>[i]` is O(1). BEAM has:

- Lists: O(n) random access, O(1) prepend. Idiomatic Erlang, wrong fit
  for TS arrays.
- Tuples: O(1) random access, O(n) "update" (because copy). Right fit for
  the *read* side; wrong fit for *write*.
- `:array` module: O(log n) read AND write. Always worse than tuples for
  reads.

**What we do:** Tuples. O(1) read matches TS. The cost is `arr.push(x)`,
which on a tuple is O(n) (build new tuple of size+1). But:

- Idiomatic TS doesn't push in tight loops; it pipelines `.map/.filter`.
  Those compile to `lists:map/filter` (after a `tuple_to_list/list_to_tuple`
  roundtrip if we keep the tuple shape) or directly to list operations
  internally.
- For code that *does* push heavily, we document the cost.

### Gap 3: No O(1) untyped object field access

TS `obj.field` on JIT-warmed code with stable shapes is O(1) (hidden
classes). On dynamic shapes it's worse. BEAM has:

- Maps: O(log n) field access. Right fit when the shape isn't known.
- Records: O(1) field access. **But the shape has to be known at compile
  time** (the record's fields are positional indices into a tuple, looked
  up by name at compile time).

**What we do, in two layers:**

- **`interface User { ... }` types → BEAM records.** We have the schema
  from TS. We emit a record definition. Field access is O(1) — matches the
  JIT-warm TS case.
- **Anonymous `{a: 1, b: 2}` literals with no interface type → BEAM map.**
  O(log n) field access. Documented as the cost of using anonymous shapes.

This neatly mirrors what TS itself does: interface-typed objects are fast
(hidden class shortcut); ad-hoc object literals are slower. Same gradient,
different absolute speeds.

### Smaller gaps that just work

- String indexing `s[i]`: O(1) on TS, O(1) on BEAM binaries. Match.
- String length: O(1) on both. Match.
- String concat: O(n+m) on both. Match.
- Array length: O(1) on TS, O(1) on BEAM tuple (`tuple_size/1`). Match.
- `.map/.filter/.reduce`: O(n) on both. Match.

## The final shape of Phase 2

The decisions table. Every row is grounded in the principle.

| TS construct                  | BEAM target          | Why                                       |
| ----------------------------- | -------------------- | ----------------------------------------- |
| `Array<T>`                    | Tuple                | O(1) read; idiomatic TS avoids O(n) push  |
| `interface Foo`-typed object  | BEAM record          | O(1) field access (matches JIT-warm TS)   |
| Anonymous `{a: 1}` literal    | BEAM map             | No schema — dynamic, O(log n) field access |
| `Map<K,V>`                    | BEAM map             | Closest available; O(log n) gap documented |
| `Set<T>`                      | BEAM map with `true` values | Same as Map                        |
| `string`                      | Binary               | O(1) access + length, fast concat         |
| Numeric literal               | BEAM integer/float   | Free upgrade: arbitrary precision         |
| `boolean`                     | `'true' \| 'false'` atoms | Native BEAM booleans                  |
| `enum Color { Red, Green }`   | Atoms (`'red'`)      | Better than TS's numbers under the hood   |
| Union types (`A \| B`)        | No runtime form      | Compile-time only, BEAM has type tags     |
| Tuple types `[string, number]`| BEAM tuple           | Direct match                              |
| `null` / `undefined`          | `nil` atom (or `undefined` atom for explicit `undefined`) | Match TS distinction; revisit |

## What we're explicitly NOT doing in Phase 2

Future plans, not this phase:

- ❌ Writing our own hashmap to get O(1). Real-world performance lose.
- ❌ Materializing union types as tagged tuples at runtime. BEAM has type
  tags; we use them at pattern-match time, not at value-construction time.
- ❌ Classes, methods, `this`. Phase 4 territory (OTP/GenServer).
- ❌ Generics at runtime. Erased like in TS today.
- ❌ Async/await, generators. Phase 3.
- ❌ Decorators. Way later.

## The build order, and why

Phase 2 has six sub-features. We build them in this order:

1. **Array literals as tuples.** `[1, 2, 3]` → `{1, 2, 3}`. Indexing, length.
   *Why first:* arrays are everywhere in TS code. Most code uses arrays
   before it uses any other data structure. Also, the smallest possible
   change to the emitter — just one new expression kind.

2. **Array methods.** `.map`, `.filter`, `.reduce`, `.length`, `.push` (as
   immutable append). *Why second:* once arrays exist, programs want to do
   things with them. These compile to `lists:*` calls or inline patterns.

3. **Anonymous object literals as BEAM maps.** `{a: 1, b: 2}`, `obj.a`,
   `{ ...obj, a: 2 }`. *Why third:* objects are the second-most-common
   shape in TS programs. We do anonymous-as-map first because it doesn't
   need the schema-tracking infrastructure that interfaces need.

4. **Strings as binaries.** Flip current emission. `"hi"` becomes
   `<<"hi">>`. `s + t`, `s.length`, `s[i]`. *Why fourth:* strings work
   "okay" today (as char lists). The switch is mechanical but touches
   existing code, so we do it after we've built confidence in the
   patterns.

5. **`Map<K,V>` and `Set<T>` constructors.** Adds the explicit
   `new Map()` / `new Set()` syntax, lowering to BEAM map ops. *Why fifth:*
   tiny surface area once anonymous maps already work.

6. **Interfaces as records.** `interface User { name: string }` →
   `-record(user, {name})`. Field access through the record. *Why last:*
   this is the biggest infrastructure addition — we need to track which
   interfaces exist, generate record headers, route typed-object field
   access through `element/2` instead of `maps:get/2`. Worth doing, but
   it's a project on top of the rest.

7. **Enums as atoms.** (Optional — can be inserted anywhere; tiny work.)

Each gets its own paired `plan_*.md` + `discussion_*.md` under
`plans/phase2/`. Discussion files for later features can be short — they
just reference back to *this* document for the principle, and discuss
construct-specific design choices.

## What this rules out (so we don't relitigate)

- ❌ "Match TS complexity exactly, even if it means writing custom data
  structures." Real-world perf loss; not worth the symmetry.
- ❌ "Lists as default for Array<T>." Loses O(1) random access. Doesn't
  match idiomatic TS expectation.
- ❌ "Hide the gaps from users." The principle is no *hidden* shock;
  documented gaps are fine.
- ❌ "Be brittle and only deliver TS's exact behavior." Big integers, TCO,
  immutability are wins we lean into.
- ❌ "Materialize union types at runtime." BEAM's built-in type tags do the
  work; no runtime overhead needed.

## What's still open

- **`undefined` vs `null`.** TS distinguishes them; BEAM has `nil`. Do we
  use two atoms (`undefined` and `nil`)? One? Reject undefined-vs-null code
  with a warning? Probably the two-atom approach; decide when we get to
  objects (step 3).
- **Negative array indices.** TS `arr[-1]` is `undefined`. BEAM
  `element(-1, T)` errors. Decide when we get to indexing (step 1).
- **Array spread `[...a, ...b]` complexity.** O(n+m) in TS. We lower to
  `erlang:tuple_to_list/1` + `++` + `list_to_tuple/1`, which is O(n+m) but
  with worse constants. Acceptable. Documented.
- **Mixed-type arrays `[1, "a", true]`.** TS allows them. BEAM tuples
  allow them. Match. No special handling needed.
