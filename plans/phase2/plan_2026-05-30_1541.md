## What this delivers

After this work, TSBeam accepts object literals, interface-typed
objects (as records for O(1) field access), `Map<K,V>`, and `Set<T>`.

Anonymous object example:

```typescript
const point = { x: 3, y: 4 }
console.log(point.x)
console.log(point.y)
const moved = { ...point, x: 10 }
console.log(moved.x)
```

Interface example (records, O(1) field access):

```typescript
interface User {
  name: string
  age: number
}

function greet(u: User): string {
  return u.name
}

const alice: User = { name: "alice", age: 30 }
console.log(greet(alice))
console.log(alice.age)
```

Map / Set example:

```typescript
const counts = new Map<string, number>([["a", 1], ["b", 2]])
console.log(counts.get("a"))
console.log(counts.has("b"))
console.log(counts.size)

const seen = new Set<number>([1, 2, 3])
console.log(seen.has(2))
console.log(seen.size)
```

## Scope

**In scope:**

- Anonymous object literals: `{ a: 1, b: 2 }` → BEAM map `#{a => 1, b => 2}`
- Identifier and string-literal keys (`{ "key with space": 1 }`)
- Shorthand `{ foo }` (= `{ foo: foo }`)
- Field access: `obj.field` → `maps:get(field, Obj)` for anonymous;
  `element(N, T)` for record-typed
- Object spread: `{...obj, a: 99}` → `Obj#{a => 99}`
- `interface` declarations recognized at the TS level; emitter consults
  TypeChecker for contextual types
- Object literals with contextual interface type compile to records
- `new Map<K,V>()`, `new Map<K,V>(iterable)` — constructor accepting
  array of pairs
- `Map.get`, `.has`, `.size`, `.delete` (returns new map), `.set`
  (REJECTED if used in-place; see "rejected" below)
- `new Set<T>()`, `new Set<T>(iterable)`
- `Set.has`, `.add` (REJECTED in-place), `.delete`, `.size`

**Rejected with helpful errors:**

- `m.set(k, v)` as a statement (where return value is discarded) —
  same reason as `arr.push`; suggests `const m2 = { ...m, [k]: v }`
- `s.add(x)` similarly when discarded

**Out of scope:**

- Computed keys `{ [expr]: val }`
- Generic interfaces `interface Box<T>`
- Interface inheritance / intersection / union types
- Optional properties (`name?: string`)
- Index signatures (`[key: string]: number`)
- `Object.keys/values/entries`
- `for...in`, `for...of`
- `Map.entries/keys/values/forEach`
- `WeakMap`, `WeakSet`

## Architecture

### Anonymous objects (the maps path)

Pure emitter additions. `ts.ObjectLiteralExpression` → BEAM map syntax.

Property access dispatch in `emitPropertyAccess` becomes routed:

1. If the operand has contextual type matching a known interface, emit
   record access (`element(N, T)`)
2. Otherwise if the property name is `.length`, emit `tuple_size`
   (existing array support)
3. Otherwise emit `maps:get(name, obj)` (anonymous map case)
4. `.size` on Map/Set → `maps:size`

Spread update `{...obj, a: 99}` lowers to `Obj#{a => 99}`. Detect the
spread by checking `expr.properties` for `SpreadAssignment`.

### Interfaces and records (the schema path)

This is the part that needs type-checker integration.

**New emitter state:**

- `interfaces: Map<string, { fields: string[] }>` — collected from
  `ts.InterfaceDeclaration` at module pass start
- `typeChecker: ts.TypeChecker | null` — set during `emitModule`

**Field ordering matters.** Records use positional indices. Two objects
of the same interface must agree on the order. We use the order in
which fields are declared in the interface — deterministic from source.

**Record emission:**

Module header includes record declarations as Core Erlang attributes.
Currently the emitter uses `attributes []` (empty); we extend to:

```text
attributes [{record, {'user', [{name, []}, {age, []}]}}]
```

Wait — actually, Core Erlang doesn't have a `-record` directive at
this level. Records in Erlang are compile-time syntactic sugar that
expand to tuples with a tag atom: `{user, "alice", 30}`. Core Erlang
sees only the tuples.

**Decision: we don't emit any record declaration in the attributes
block.** Instead, we emit tagged tuples directly:

- Construction: `{ name: "alice", age: 30 }` of type `User` →
  `{'user', "alice", 30}` (Core Erlang tuple with type-tag atom first)
- Field access: `u.name` → `element(2, U)` (slot 2 because slot 1 is
  the tag)
- Indices computed from the interface field order at compile time.

This matches what `erlc` would produce from Erlang source with
`-record(user, {name, age}). U#user.name`.

**Contextual type detection:**

When emitting `{ name: "x", age: 1 }`, we check via the TS type
checker:

```typescript
const contextualType = typeChecker.getContextualType(objectLiteralNode)
if (contextualType && /* it's one of our known interfaces */) {
  // emit as record
} else {
  // emit as anonymous map
}
```

Same check on `expr.expression` for `PropertyAccessExpression`: if
the expression's type is a known interface, route through record
access.

**When type info is unavailable:**

Fallback to anonymous map. The user gets the slower O(log n) path but
correct behavior. We never emit incorrect code due to missing type
info.

### Map and Set

`new Map<...>(iterable)` → call sites:

- Empty constructor: `new Map()` → `#{}`
- With iterable: `new Map([["a", 1], ["b", 2]])` →
  `maps:from_list([{"a", 1}, {"b", 2}])`. Iterable must be an array
  literal of pairs in this round; arbitrary iterables out of scope.
- `new Set([1, 2, 3])` → `maps:from_list([{1, true}, {2, true}, {3, true}])`

Method dispatch in `emitMethodCall` gets new entries:

- `m.get(k)` → `call 'maps':'get'(K, M, 'undefined')` (third arg
  prevents badkey crash; matches TS Map returning undefined for missing
  keys — though we don't have undefined yet; use `'undefined'` atom)
- `m.has(k)` → `call 'maps':'is_key'(K, M)`
- `m.delete(k)` → `call 'maps':'remove'(K, M)`
- `m.size` (PropertyAccess, not method) → `call 'maps':'size'(M)`
- `s.add(x)` → REJECT
- `m.set(k, v)` → REJECT

Detection of "Map vs anonymous object" is done structurally: if the
receiver is a `new Map()` / `new Set()` call (we'd need type info to
detect via `Map<K,V>` variable annotations), it's a Map.

**Simpler initial path:** since `m.get(...)` is unambiguous syntax,
we don't need to distinguish Map from object at the *use* site. Both
work the same way (both are BEAM maps; `maps:get` works on any of
them). The distinction is at construction.

We can also support `.get(k)`, `.has(k)` on anonymous objects — same
lowering. Idiomatic TS doesn't do this (objects use `obj.k`, Maps use
`m.get(k)`) but the underlying primitive is identical, so it Just
Works either way.

### Step 3: interfaces as records

This is the big one. Three sub-steps:

#### 3a: collect interfaces at module scope

- Add `interfaces: Map<string, { fields: string[] }>` field to Emitter
- Populate during `emitModule`: walk `sourceFile.statements`, capture
  every `InterfaceDeclaration`
- Field order = declaration order in the source

#### 3b: integrate the TypeScript type checker

- `parseSourceFile()` already creates a `ts.Program`. Save it to the
  Emitter alongside the source file.
- New emitter method `getInterfaceTypeName(expr): string | null` that
  returns the interface name (e.g. `"User"`) if `expr`'s contextual or
  declared type matches one of our collected interfaces, else null.
- Uses `program.getTypeChecker()` and `.getContextualType()` /
  `.getTypeAtLocation()`.

#### 3c: route through records when type matches

- In `emitObjectLiteral`: if the expression's contextual type is a
  known interface, emit a tagged tuple `{'name_lc', ...fields_in_order}`
  instead of a map. Tag is the interface name lowercased.
- In `emitPropertyAccess`: if the operand's type is a known interface,
  emit `element(N, T)` where N is `1 + fieldIndex(name) + 1` (slot 1 is
  tag, fields start at slot 2).

Failing fixtures:

- `interface_basic.ts` — declare User, construct, access fields
- `interface_in_function.ts` — pass User to a function, return User
- `interface_two.ts` — two interfaces in same module, used together
- `interface_with_spread.ts` — `{ ...userA, age: 31 }` of type User
- `interface_mixed.ts` — interface objects and anonymous maps in same
  program (each uses its own representation)

Run, generate baselines.

## Implementation notes

Went through cleanly. Final state: 9 new positive fixtures (objects,
Map, Set, interfaces), 2 new negative fixtures (rejected in-place
mutators). 48 total passing before strings work; 52 after.

1. **Core Erlang map syntax uses tildes, not hashes.** `~{ 'k' => v }~`
   for literals, `~{ 'k' => v | _Base }~` for spread updates. Different
   from the Erlang surface syntax (`#{...}` and `M#{k => v}`).

2. **Records aren't a Core Erlang construct.** Erlang's `-record(...)`
   is surface-level syntactic sugar that expands to tagged tuples. We
   emit the tuples directly: `{'user', "alice", 30}`. Slot 1 is the
   atom tag (interface name lowercased); fields start at slot 2. This
   matches what `erlc` would produce from Erlang record syntax.

3. **The type checker integration was straightforward.** Added
   `typeChecker: ts.TypeChecker | null` to Emitter, passed it down
   from `build.ts` via `program.getTypeChecker()`. The helper
   `interfaceNameFor(expr)` consults `getContextualType` then
   `getTypeAtLocation` as fallback. Works through function parameter
   types, return type annotations, and explicit `const x: User = ...`.

4. **Interface declarations have to be skipped during the
   top-level-statement pass.** Initially missed this — interfaces were
   getting collected but then re-encountered as `InterfaceDeclaration`
   statements, which the emitter doesn't know how to emit. Fixed by
   adding an `if (ts.isInterfaceDeclaration(stmt)) continue` at the
   top of the second loop.

5. **Spread update on records uses `setelement/3`.** Each overridden
   field becomes one `setelement` call layered on the base. For
   `{...alice, age: 31, name: "bob"}`, this is two nested setelements.
   Acceptable for now; could optimize to a single tuple rebuild later
   if benchmarks matter.

6. **Map/Set methods on anonymous objects also work.** `obj.get(k)`,
   `obj.has(k)` on a regular `{a: 1}` map literal — both compile
   correctly because anonymous objects and Map are the same BEAM
   primitive. We don't enforce the syntactic distinction at the use
   site.

No deviations from scope. Open questions 1-4 in this plan all
resolved as expected during implementation.

## Open questions

1. **Printing.** `console.log(point)` for `{ x: 3, y: 4 }` will print
   the BEAM map syntax `#{x => 3, y => 4}`. Acceptable for now; we may
   want a TS-friendly formatter later.

2. **Map.size as property vs method.** TS spec says `.size` is a
   property (no parens). We handle it in `emitPropertyAccess`, not
   `emitMethodCall`. Same code path as `array.length`.

3. **Interface field order across modules.** Not relevant in this
   round (single-module compilation), but interface schemas live on
   the emitter instance only. If we ever support multi-module
   compilation, we need a shared interface registry.

4. **Records vs `.set` mutability.** Records don't support
   `Object.set` style mutation; spread update `{...user, age: 31}`
   on an interface-typed object lowers to `setelement(N, T, V)`. Need
   to confirm that's the right call (alternative: rebuild the tuple).
