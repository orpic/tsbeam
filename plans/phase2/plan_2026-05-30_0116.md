## What this delivers

After this work, TSBeam accepts arrow functions and the five core array
methods. The following program will compile and run:

```typescript
const xs: number[] = [1, 2, 3, 4, 5]

const doubled = xs.map(x => x * 2)
const evens = xs.filter(x => x % 2 === 0)
const total = xs.reduce((acc, x) => acc + x, 0)
const found = xs.indexOf(3)

xs.forEach(x => console.log(x))
console.log(doubled[0])
console.log(evens.length)
console.log(total)
console.log(found)
```

The following will be **rejected at compile time** with helpful errors:

```typescript
xs.push(6)            // error: arrays are immutable; use [...arr, 6] instead
xs.pop()              // same family
xs.shift()
xs.unshift(0)
xs[0] = 99            // error: cannot assign to array index; arrays are immutable
```

## Scope

**In scope:**

- Arrow function expressions: `(x) => x + 1`, `(x, y) => x + y`, `() => 42`
- Arrow function bodies: both expression form `x => x + 1` and block form
  `x => { return x + 1 }`
- Lexical capture (closure over enclosing `let`/`const` bindings)
- Five array methods: `.map`, `.filter`, `.reduce`, `.forEach`, `.indexOf`
- `.reduce(f, init)` — two-arg form **only**; one-arg form rejected
- Compile-time rejection of mutating methods (`.push`, `.pop`, `.shift`,
  `.unshift`) and index assignment (`arr[i] = x`)
- Single-argument callback form only (`.map(x => ...)`); rejecting
  callbacks that destructure index or whole-array

**Out of scope:**

- `%` (modulo) operator — if the win-condition uses it, add to arithmetic
  emitter as a small dependency. Verify in step 0.
- Array spread `[...a, ...b]` (next step)
- Other array methods: `.find`, `.findIndex`, `.some`, `.every`,
  `.slice`, `.concat`, `.includes`, `.join`, `.flat`, etc.
  (bundled follow-up step)
- Standalone function expressions (`function (x) { return x }`) — defer;
  arrow functions cover the use case.
- `this`-binding semantics (no `this` in arrows by spec — natural for us)
- Async arrow functions (Phase 3)
- Default parameters, rest parameters in arrows
- Generic arrow functions `<T>(x: T) => x`

## Architecture

Two emitter additions, one new dispatch table:

### 1. Arrow function emission

`ts.ArrowFunction` → Core Erlang `fun (X, Y) -> <body> end`.

For expression-body form (`x => x + 1`), the body is one expression.
For block-body form (`x => { ... return ... }`), reuse the existing
`emitBlock` logic — the block is already a sequence of statements with
returns being terminal after lowering.

Note: ArrowFunction's parameters need to flow through
`tsParamName` like FunctionDeclaration parameters, so `_x`, `_y` etc.

### 2. Method dispatch for `.method()` calls on arrays

Extend `emitCall` to detect property-access calls like `xs.map(f)`:

- If the property name is in the **supported set** (`map`, `filter`,
  `reduce`, `forEach`, `indexOf`), emit the Core Erlang shape below.
- If it's in the **rejected set** (`push`, `pop`, `shift`, `unshift`),
  throw with a helpful error suggesting the immutable alternative.
- Otherwise, fall through to the existing "unsupported call" path (which
  will become object method dispatch later).

### 3. Index-assignment rejection

`arr[i] = x` parses as `BinaryExpression { left: ElementAccess, op: =, right }`.
Detect this shape in `emitBinary` and throw a helpful error.

### Lowering style for each method

In all of these, `T` = the tuple, `F`/`P` = the callback, `Init` = the
initial value, `Target` = `.indexOf` argument.

**Revised from earlier draft:** the original plan called for list
comprehensions (`[F(X) || X <- L]`). Sanity-checking in `local_sandbox/`
showed that `erlc +from_core` rejects that syntax — Core Erlang at this
level doesn't appear to surface comprehensions. We drop to plain
`lists:map`/`lists:filter` calls, which compile cleanly and run correctly.
The discussion file's "list comprehension" framing is now stale; treat
this table as authoritative.

- `xs.map(f)` → `call 'erlang':'list_to_tuple'(call 'lists':'map'(F, call 'erlang':'tuple_to_list'(T)))`
- `xs.filter(p)` → `call 'erlang':'list_to_tuple'(call 'lists':'filter'(P, call 'erlang':'tuple_to_list'(T)))`
- `xs.reduce(f, init)` → `call 'lists':'foldl'(F, Init, call 'erlang':'tuple_to_list'(T))`
- `xs.forEach(f)` → `call 'lists':'foreach'(F, call 'erlang':'tuple_to_list'(T))`
- `xs.indexOf(target)` → hand-written; see below

**`xs.indexOf(x)` lowering** — we hand-write a small helper at the call
site using an anonymous fun and `lists:foldl`:

```text
let <_target> = X
in let <_list> = call 'erlang':'tuple_to_list'(T)
   in (case
         call 'lists':'foldl'(
           fun (_E, _Acc) ->
             case _Acc of
               {'found', _I} when 'true' -> _Acc
               {'searching', _I} when 'true' ->
                 case call 'erlang':'=:='(_E, _target) of
                   'true' when 'true' -> {'found', _I}
                   'false' when 'true' -> {'searching', call 'erlang':'+'(_I, 1)}
                 end
             end
           end,
           {'searching', 0},
           _list) of
         {'found', _I} when 'true' -> _I
         {'searching', _} when 'true' -> call 'erlang':'-'(1)
       end)
```

We confirm this shape works in `local_sandbox/` before emitting it
(step 0 below).

Anonymous `fun (..) -> ... end` is needed inside the `.indexOf` helper.
Same construct used by arrow function emission, so it's free once arrows
work.

## Implementation notes

Went through the six steps largely as written. Key findings:

1. **Core Erlang doesn't accept the list comprehension syntax** I tried in
   step 0 (`[F(X) || X <- L]` at this level of the language). `erlc
   +from_core` rejected it with `syntax error before: '|'`. Switched the
   plan to use `lists:map` / `lists:filter` instead. Same big-O, slightly
   different code shape, runs cleanly. The "list comprehensions are more
   idiomatic" claim in the discussion file is now stale — `lists:map` is
   equally idiomatic here.

2. **Calling a let-bound fun value needs different emission than calling
   a module-level function declaration.** Module fns use `apply
   'name'/arity(args)`; bound funs use `apply _name(args)`. The emitter
   now tracks `moduleFunctions: Set<string>` populated at the start of
   `emitModule` and dispatches accordingly in `emitCall`. Without this,
   `const double = ...; double(7)` would emit `apply 'double'/1(7)` and
   fail to link.

3. **`emitCall`'s dispatch order matters.** It's:
   1. `console.log` (special-case the I/O sink)
   2. Property-access calls (`x.method(...)`) — routes to method dispatch
      or rejection
   3. Identifier calls — routes by `moduleFunctions` lookup

   Property-access has to come before identifier-call because both
   eventually consume a `CallExpression`, but only one of them applies.

4. **The `.indexOf` helper compiles to about 15 lines of Core Erlang per
   call site.** This is fine — the alternative was generating a per-module
   helper function, which would have added emitter complexity. Inline is
   cheap and predictable. The Core Erlang compiler likely inlines small
   funs anyway.

5. **Rejection errors fire at compile time as designed.** Manually
   verified in `local_sandbox/` (push_rejected.ts, index_assign_rejected.ts).
   The compiler exits non-zero, prints the helpful message, no output is
   generated. Did not add an automated rejection-test harness in this
   step — that's a separate small piece of infrastructure for later.

6. **Closure capture works automatically.** `arrow_capture.ts` (closes
   over an outer `const`) passed on the first try because Core Erlang
   `fun` already closes over the lexical environment. No special handling
   needed in the emitter. This is one of the BEAM "free wins" mentioned
   in the parent Phase 2 discussion.

7. **Pipeline calls (`.filter().map()`) work but generate redundant
   tuple↔list roundtrips.** Inspect `tests/.build/array_pipeline/array_pipeline.core` —
   each method does its own `tuple_to_list` and `list_to_tuple`. For
   pipelines, half of these conversions are wasted (the list could flow
   directly from filter to map). This is an optimization opportunity for
   later (fusion pass under `src/compiler/lower/`), not a correctness
   issue.

No deviations from scope. All eight new fixtures pass; rejection paths
work. Total 21 fixtures passing.

## Open questions to resolve during implementation

1. **Arity rejection.** `xs.map((x, i) => ...)` — TS callback takes
   (element, index, array). Plan says reject anything beyond
   single-element. Confirm in step 3 how clean the rejection logic is.
2. **Block-body arrows.** `(x) => { const y = x * 2; return y }`. The
   block already supports `let` and `return` from Phase 1. Verify in
   step 2.
3. **`.reduce` one-arg form.** `xs.reduce(f)` without an initial value is
   a runtime error in TS for empty arrays. Plan says reject one-arg form
   at compile time. Confirm in step 3.
4. **Type annotations in arrows.** `(x: number) => x * 2` and
   `(x: number): number => x * 2` both legal in TS. Both should parse
   and emit fine (types erased). Confirm.
5. **The `%` operator** for modulo. If we use it in a test fixture, we
   need to add it to `binaryOpToErlang`. BEAM has `rem` for integer
   modulo. Decide during step 1 whether any fixture needs it; if so,
   add the mapping. Plan currently uses `> 2` instead of `% 2 === 0` to
   avoid needing modulo for now.
