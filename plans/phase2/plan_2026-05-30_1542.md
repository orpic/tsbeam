## What this delivers

TS string operations get O(1) `length`, O(1) indexed access, O(n+m)
concat — matching TS complexity.

```typescript
const s: string = "hello"
console.log(s.length)        // 5
console.log(s[0])            // "h" (one-byte binary)
console.log(s + " world")    // "hello world" (printed as <<"hello world">>)
```

## Scope

**In scope:**

- String literal emission as BEAM binaries: `"hello"` → `<<"hello"/utf8>>`
- `s.length` → `byte_size(S)`
- `s[i]` → `binary:part(S, I, 1)` (returns one-byte binary, matches TS
  single-char string semantics)
- `a + b` where both operands are typed `string` →
  `<<A/binary, B/binary>>`
- Type-checker integration to detect string-typed expressions

**Out of scope:**

- Template literals (`` `hello ${name}` ``) — separate later step
- `String` methods (`.toLowerCase`, `.slice`, etc.) — bundled later
- Unicode-aware indexing (code points vs bytes) — accept byte indexing
- Printing improvements (`<<"hi">>` vs `"hi"`) — deferred to runtime
  library work
- `String(...)` coercion function

## Architecture

### Type-aware emission

Reuses the TypeChecker added during interfaces work. New helper:

```typescript
private isStringType(expr: ts.Expression): boolean {
  if (!this.typeChecker) return false
  const t = this.typeChecker.getTypeAtLocation(expr)
  return (t.flags & ts.TypeFlags.StringLike) !== 0
}
```

### Three call sites

1. **String literal emission.** In `emitExpression`, the
   `ts.isStringLiteral` branch changes:

   ```typescript
   if (ts.isStringLiteral(expr)) {
     return `<<${JSON.stringify(expr.text)}/utf8>>`
   }
   ```

2. **Binary `+` operator.** In `emitBinary`, detect string-concat:

   ```typescript
   if (op === SyntaxKind.PlusToken &&
       (this.isStringType(expr.left) || this.isStringType(expr.right))) {
     // emit <<L/binary, R/binary>>
   }
   ```

3. **`.length` and indexed access.** Already type-dispatched after
   interfaces work; just add the string branch:
   - `s.length` → `call 'erlang':'byte_size'(${operand})`
   - `s[i]` → `call 'binary':'part'(${operand}, ${index}, 1)`

### Fallback when type info is missing

If `isStringType` returns false (no type info, or type isn't a string),
keep existing behavior. This means:

- A string literal with no contextual type still emits as binary
  (literals always have type)
- `a + b` where types are unknown defaults to integer addition (current
  behavior)
- `a.length` where type is unknown defaults to `tuple_size` (current
  behavior)

This is correct because the fallback paths still produce *some* code
that compiles; users will hit runtime crashes if they meant string ops
but the type info was wrong. The type checker's job is to make this
rare.

## Implementation notes

Went through in one pass. Final state: 4 new positive fixtures
(string_length, string_index, string_concat, string_concat_var). 52
total passing.

1. **Core Erlang's `<<"hello">>` shorthand doesn't work at this level.**
   The high-level Erlang surface syntax got rejected by
   `erlc +from_core`. Had to fall back to the canonical Core Erlang
   binary-segment syntax: `#{#<104>(8, 1, 'integer', ['unsigned', 'big']),
   ...}#`. Each byte gets its own segment. Verbose to emit but no
   runtime cost — `erlc` collapses to the same BEAM bytecode either
   way.

2. **Binary concat needs the `'binary'` segment type, not `'integer'`.**
   For `<<A/binary, B/binary>>` style concat we emit:
   `#{#<A>('all', 8, 'binary', ['unsigned', 'big']),
      #<B>('all', 8, 'binary', ['unsigned', 'big'])}#`. The `'all'` size
   means "use whole binary"; unit is 8 bits.

3. **`typeof` needed updating.** It was comparing to char-list strings
   (`"number"`, `"string"`) which no longer match the new binary
   string literals. Also the `is_list` guard for the `"string"` branch
   was now wrong — strings are binaries. Updated typeof to return
   binaries and use `is_binary` in the string branch. Surfaced as a
   real bug in `combo_mixed_filter` (`typeof x === "number"` returned
   false for everything, filter dropped all elements, then `numbers[0]`
   crashed on empty tuple).

4. **5 existing baselines needed regeneration.** Anywhere we previously
   printed strings via `~p`, the output changed from `"text"` to
   `<<"text">>`. Reviewed each diff before accepting:
   - `array_mixed_types`, `object_shorthand`, `interface_basic`,
     `interface_with_spread`, `combo_arrow_captures_element`.

5. **No surprises with `+` operator dispatch.** TS type checker
   correctly identifies string operands; string concat fires for all
   the expected cases. Integer addition continues to work where neither
   operand is a string.

6. **`s[i]` returns a one-byte binary, not an integer.** Used
   `binary:part(S, I, 1)` (returns binary) instead of `binary:at(S, I)`
   (returns integer byte). This matches TS's "indexing returns a
   one-character string" semantics.

No deviations from scope. The ugly `<<"...">>` print output is the
known cost, documented and deferred to a future runtime-library plan.

## Open questions

1. **`~p` printing.** Strings will print as `<<"text">>`. Acceptable
   for this step; ugly enough that we'll want to fix it in a runtime
   library plan soon.

2. **String comparison.** TS `===` on strings works at the value
   level. BEAM `=:=` on binaries is bytewise comparison — same answer.
   No special handling needed.

3. **String methods.** Out of scope here. When we add `.slice`,
   `.toUpperCase`, etc., we'll route through `binary` module / our own
   helpers. Plan that round when it comes.
