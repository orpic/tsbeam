# Why array methods + arrow functions ship together

**Date:** 2026-05-30 01:16 (local)
**Paired plan:** [plan_2026-05-30_0116.md](plan_2026-05-30_0116.md)
**Parent discussion:** [discussion_2026-05-30_0058.md](discussion_2026-05-30_0058.md)
(the Phase 2 principle as a whole)

This is step 2 of Phase 2. Step 1 made array literals and `arr[i]` work
(arrays-as-tuples, O(1) read, `.length`). This step makes arrays *useful*
— `.map`, `.filter`, `.reduce`, `.forEach`, `.indexOf` — and adds arrow
functions, because nobody calls `.map` with a named function in practice.

The Phase 2 principle (no negative shocks, lean into BEAM wins) is in the
parent discussion. This file covers the design choices specific to
methods and arrows.

---

## Why arrows and methods land together

In idiomatic TS, you basically never see:

```typescript
function double(x: number): number { return x * 2 }
const ys = xs.map(double)
```

You see:

```typescript
const ys = xs.map(x => x * 2)
```

So if we shipped array methods first and arrows later, the headline
feature wouldn't work for any real code. The two features are functionally
paired even though they're conceptually separate.

The split between steps used to be "one syntactic feature per step." That
worked when each feature stood alone. For methods, it doesn't — methods
*are* function application, which needs functions. We pair them.

---

## Why list comprehensions instead of `lists:map` etc.

When you call `xs.map(f)` and `xs` is a tuple, BEAM has two natural
lowerings:

**Path A: Use the `lists` module.**

```
list_to_tuple(lists:map(F, tuple_to_list(Xs)))
```

This works. It's three function calls per `.map`: convert to list, run
`lists:map`, convert back. Two of those calls are O(n) — same big-O as the
map itself.

**Path B: Use a Core Erlang list comprehension.**

```
list_to_tuple([F(X) || X <- tuple_to_list(Xs)])
```

The comprehension is one O(n) pass building a fresh list. Then one
`list_to_tuple` (O(n)). Same big-O as path A, but one fewer pass — we skip
the intermediate `lists:map` walk.

Real difference is small (a constant factor), but **path B is what an
Erlang programmer would write by hand.** That matters to us — TSBeam's
generated Core Erlang should look like something a human would write, not
like a transpiler's broken English. We're not optimizing for runtime
speed yet; we're optimizing for code that BEAM people would read and
nod at.

For `.reduce` and `.forEach` the comprehension idiom doesn't apply (those
aren't shape-preserving traversals). Those use `lists:foldl/3` and
`lists:foreach/2` — also idiomatic.

`.indexOf` doesn't fit any standard helper cleanly — it returns a specific
index, with a sentinel (`-1`) for "not found." We hand-write a small
helper using `lists:keyfind`-style recursion, emitted inline at the call
site. Slightly more code at the emit site; keeps the lowering local and
predictable.

## Why we reject `.push` instead of pretending it works

`.push` in TS:

1. Mutates the array in place.
2. Returns the new length.

We can match neither without breaking the world:

- We can't mutate — BEAM values are immutable, and `const xs` in TS means
  `xs` is rebound (not the underlying object). Even if `xs` were `let`,
  rebinding doesn't compose with how we emit `let` bindings as Core Erlang
  `let X = ... in ...`.
- We could *return* a new tuple from `push`, but then `xs.push(x)` doesn't
  modify `xs` — it just builds a new tuple that gets thrown away unless
  you assign it. That's a silent footgun.

The pragmatic options:

- **Silently change semantics** to "return a new array." Programs would
  break in subtle ways. Worst possible outcome.
- **Accept `.push` but issue a runtime warning.** Doesn't help — by the
  time the program runs, the user's already invested.
- **Reject `.push` at compile time with a helpful error.** Best outcome
  for the principle.

The principle says: **no negative shocks at runtime, and where TS idiom
diverges from immutable-style idiom, push the user toward the latter.**
Rejecting `.push` enforces that idiomatic-TS-on-TSBeam means
`[...arr, x]`, which compiles cleanly. The error message tells them
exactly that.

Same reasoning applies to `.pop`, `.shift`, `.unshift`, and `arr[i] = x`.
All mutate. All get rejected with helpful errors pointing at the
immutable alternative.

The other rejected mutators get the same treatment as `.push` even if a
user could *theoretically* tolerate "returns new array" semantics for
some of them (e.g. `.shift` returning a new array would match TS's
contract less badly than `.push`). We reject the whole family for
consistency — one rule is easier to teach than four.

## Why we don't add `[...arr, x]` (spread) right now

Spread is the right alternative to `.push`. But spread is itself a
language feature we haven't added yet:

- Array spread `[...a, ...b]`
- Object spread `{...obj, field: x}` (Phase 2 later step)
- Function-call spread `f(...args)`
- Rest parameters `function f(...args) {}`

These all share AST shape (`SpreadElement`, `SpreadAssignment`) but
different semantics. We could do array spread alone now, but:

- It's a clean separate step. Adding it inline doubles the scope of *this*
  step.
- The `.push` error message can suggest `[...arr, x]` as the alternative
  *even though we don't accept it yet* — the error becomes the
  documentation for what we're about to add.

So in this step, `[...arr, x]` is recommended in errors but not yet
accepted. Next step (or one after) adds it. The slight UX wrinkle of
"the error suggests something not yet supported" is acceptable for one
or two steps' overlap; the alternative (delaying methods until spread
ships) is worse.

---

## Why we add `.indexOf` even though it's a "find" not a "map"

`.indexOf` doesn't fit the functional-pipeline shape (`map → filter →
reduce`). It's a single-element query. So why include it?

Because it's the most common TS array method that doesn't have an
obvious BEAM equivalent. Skipping it would force users to write a
recursive helper for "does this array contain X" — which is exactly the
kind of friction the "no negative shocks" principle says to avoid.
Adding it is ~20 lines of emitter code; the cost-benefit clearly favors
including it.

We do **not** add `.find`, `.findIndex`, `.some`, `.every` in this step.
Each is its own variant of the same recursive walk. They'll come in a
follow-up step bundled together. This keeps the step bounded.

---

## What about arrow function semantics — capturing variables?

TS arrows close over their lexical scope. So this:

```typescript
const factor = 3
const ys = xs.map(x => x * factor)
```

…depends on `factor` being captured by the arrow.

Core Erlang `fun` expressions also capture lexically. So this lowers
cleanly:

```
let <_factor> = 3 in
  let <_ys> = list_to_tuple([call 'erlang':'*'(_X, _factor) ||
                             _X <- tuple_to_list(_xs)])
  in ...
```

The `_factor` reference inside the arrow body resolves to the enclosing
`let`. BEAM handles this natively. No extra work in the emitter — we just
have to emit the arrow body using the same `emitExpression` we use
elsewhere, with the arrow's parameters in scope.

This is one of the BEAM "free wins" we lean into. JS closures over
mutable variables are a famous footgun; BEAM closures over immutable
bindings are unambiguous.

**One nuance:** TS allows mutable captures (e.g. closing over a `let i`
whose value changes after the arrow is defined). BEAM doesn't. For now we
don't have mutable bindings anyway (`let` and `const` both lower to
immutable Core Erlang lets). When we do add mutable bindings — if we ever
do — we'll need to revisit. Not a problem in this step.

## What this rules out (so we don't relitigate)

- ❌ Roundtrip via `lists:map` etc. for shape-preserving ops. List
  comprehensions are more idiomatic Core Erlang.
- ❌ Generating custom `tuple_map` / `tuple_filter` helpers per module.
  Comprehensions are equivalent, simpler.
- ❌ Switching arrays to internal list representation just to make
  methods native. Breaks the O(1) `arr[i]` promise from step 1.
- ❌ Accepting `.push` with new "returns new array" semantics. Footgun.
- ❌ Silent semantic change for any mutator. Always reject with a
  helpful error.
- ❌ Adding array spread (`[...a, ...b]`) in this step. Separate step.
- ❌ Adding `.find`, `.findIndex`, `.some`, `.every`. Bundled follow-up.

## What's still open

- **`.indexOf` with non-primitives.** TS `.indexOf` uses `===`
  (reference equality for objects). BEAM's `=:=` is structural equality.
  Different behavior for object arrays, but we don't have objects yet, so
  this resolves itself for now. Revisit when objects land.
- **Arity mismatch errors.** What if a user writes
  `xs.map((x, i, arr) => ...)`? TS's `.map` callback takes 3 args; the
  user might rely on `i` (the index) or `arr` (the whole array). We
  could:
  1. Accept it and pass all three.
  2. Accept only single-arg callbacks; reject the rest.

  My instinct: accept only single-arg in this step (the 90% case), reject
  with a clear error for higher arities. Add multi-arg support later if
  there's demand. Document in the plan.
- **Returning `undefined` from `.forEach` callbacks.** BEAM doesn't have
  `undefined`; `lists:foreach` doesn't care what the callback returns. We
  emit whatever the body returns and let it get discarded. Fine for now.
- **Empty-array edge cases.** `[].map(f)` should be `{}`. `[].reduce(f)`
  *without an initial value* is a runtime error in TS — we'll require the
  initial value form (`reduce(f, init)`) for now and reject the unary
  form with a clear error.
