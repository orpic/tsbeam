## What this delivers

After this work, TSBeam accepts array literals, array indexing, and `.length`.
The following program will compile and run on BEAM:

```typescript
const xs: number[] = [10, 20, 30]
console.log(xs[0])         // 10
console.log(xs[2])         // 30
console.log(xs.length)     // 3

function sum(arr: number[]): number {
  return arr[0] + arr[1] + arr[2]
}
console.log(sum(xs))       // 60
```

## Scope

**In scope:**

- Array literal expressions: `[1, 2, 3]`, `[]`, `["a", "b"]`, `[1, "a", true]`
- Indexed access: `arr[i]` where `i` is a numeric literal or identifier
- `.length` property
- Type annotations: `number[]`, `Array<number>` (both accepted, erased at runtime)
- Arrays as function parameters and return values

**Out of scope** (each gets its own plan):

- Array methods (`.map`, `.filter`, `.reduce`, `.push`, `.pop`, etc.)
- Spread `[...arr]` and rest `...args`
- Destructuring `const [a, b] = arr`
- Array slicing `arr.slice(1, 3)`
- Negative indices (`arr[-1]`) — decide when methods land
- Out-of-bounds access semantics — BEAM errors, TS returns `undefined`; we'll error for now and revisit
- Mutation `arr[i] = x` — defer; idiomatic TS doesn't do this much anyway

## Architecture

Two emitter additions, one lowering decision deferred:

### Emitter additions

1. **`ArrayLiteralExpression`** → Core Erlang tuple syntax `{e1, e2, ..., eN}`.
2. **`ElementAccessExpression`** (the `arr[i]` form) → `call 'erlang':'element'(I+1, Arr)`.
   Note the **+1**: Core Erlang `element/2` is 1-indexed; TS is 0-indexed.
3. **`PropertyAccessExpression` with `.length`** on an array → `call 'erlang':'tuple_size'(Arr)`.

### Lowering: not needed for this step

Array literals and indexing are pure expression-level rewrites. No
statement-level lowering required. We do **not** create a new lowering pass
for this step. (Methods like `.map` may need one when we add them.)

### Why `element/2` and not `:array` module

`element/2` is O(1) on tuples. The `:array` module is O(log n) and would
add a runtime dependency. Tuples + `element/2` is the right primitive.

## Implementation notes

Implementation went straight through the steps without surprises. Key
observations:

1. **No lowering pass needed.** Array literals and indexing are pure
   expression-level rewrites in the emitter. Confirms the plan's call.

2. **`element/2` is 1-indexed; TS is 0-indexed.** Added a small helper
   `emitOneIndexedIndex` that constant-folds numeric literals
   (`0` → `1`, `2` → `3`) and falls back to `call 'erlang':'+'(I, 1)` for
   non-literals. Avoids `0 + 1` in the output for the common case.

3. **`.length` is hardcoded to `tuple_size/1` for now.** When strings
   become binaries (step 4) and objects become maps (step 3), we'll need
   real dispatch — but for now, only arrays have `.length` in supported
   programs, so this works. Documented as open question 4.

4. **String formatting via `~p`.** `array_mixed_types.ts` prints `"two"`
   with quotes because BEAM's `~p` formatter shows char-list strings that
   way. The baseline reflects the actual current behavior — when we
   switch to binaries in step 4, this will become unquoted automatically.

5. **`local_sandbox/` works well as the hand-write space.** Used it for
   the Core Erlang sanity check before touching the emitter. Updated
   `.gitignore`, `AGENTS.md`, and `CONTRIBUTING.md` to point at it.

No reshuffling of the plan needed. All five fixtures pass cleanly.

## Open questions to resolve during implementation

1. **String output formatting.** `~p` in `io:format` prints strings as
   `"two"` (with quotes) for char-list-based strings. After Phase 2 step 4
   (strings as binaries), this changes. For this step, expected outputs
   may show quoted strings — note in baselines whether this is the actual
   behavior or whether we need a different format specifier. **Likely
   resolution: leave it; Phase 2 step 4 fixes the string display.**

2. **Out-of-bounds indexing.** TS `arr[99]` on a 3-element array returns
   `undefined`. BEAM `element(100, T)` raises a `badarg` exception. For
   this step we let BEAM error — it's the safer default and matches
   "no hidden shocks" only loosely (the shock is "crash" instead of
   "undefined value"). Revisit when we have a clear `undefined` story.

3. **Negative indices.** TS `arr[-1]` returns `undefined`. We reject
   negative literal indices at compile time? Or pass through and let BEAM
   error? **Tentative:** pass through; document. Add a fixture later if
   needed.

4. **Property access disambiguation.** `arr.length` and `obj.field` look
   identical syntactically. The emitter needs to know which is which.
   Options:
   - Type-check: if the operand is a tuple (arrays), use `tuple_size`;
     if it's a map (objects), use `maps:size`.
   - Heuristic: hardcode the names `length` for now, treat as
     `tuple_size`. When objects land, decide if there's a field-name
     collision (probably not — TS objects shouldn't have a `length`
     field).
   - Compile-time type lookup via TS type checker.
   - **Tentative:** hardcode `.length` → `tuple_size/1` for now. When we
     add string `.length` (Phase 2 step 4) and object fields (Phase 2
     step 3), revisit with proper dispatch. Should work because TS code
     doesn't typically have `.length` fields on objects.

5. **Trailing commas in array literals.** `[1, 2, 3,]`. TS allows. Should
   work transparently because we walk children, but worth a quick test.
