# Why we're closing Phase 2 with objects, Map/Set, interfaces

**Date:** 2026-05-30 15:41 (local)
**Paired plan:** [plan_2026-05-30_1541.md](plan_2026-05-30_1541.md)
**Parent discussion (Phase 2 principle):** [discussion_2026-05-30_0058.md](discussion_2026-05-30_0058.md)

This is steps 3, 5, and 6 of Phase 2, bundled. (Step 4 — strings as
binaries — gets its own paired pair because it's orthogonal and touches
existing emission instead of adding new constructs.)

If you've read the plan and you're wondering why three steps land in
one chunk, why interfaces are "the same as objects but with a schema,"
or why we're adding `Map<K,V>` last instead of first — read on.

---

## The three steps share one underlying primitive: the BEAM map

The Phase 2 principle decision matrix said:

| TS construct                  | BEAM target          |
| ----------------------------- | -------------------- |
| Anonymous `{a: 1}` literal    | BEAM map             |
| `Map<K,V>`                    | BEAM map             |
| `Set<T>`                      | BEAM map with `true` values |
| `interface Foo`-typed object  | BEAM record          |

Three of the four are BEAM maps. The fourth (records, for typed objects)
shares half the emitter code — both deal with key→value structures, both
need field-access lowering, both need spread-update lowering. Doing
them as one chunk lets us write the shared lowering once and reuse it.

If we did anonymous objects, then `Map<K,V>`, then interfaces in three
separate rounds, we'd refactor the same code three times. Each addition
would say "wait, the way I did `obj.field` for anonymous objects needs
to be different for `Map.get` and different again for records." Better
to design the dispatch once.

---

## Anonymous objects are the easy starting point

`{a: 1, b: 2}` lowers cleanly to `#{a => 1, b => 2}` (BEAM map literal
syntax). Field access `obj.a` lowers to `maps:get(a, Obj)`. Spread
update `{...obj, b: 99}` lowers to `Obj#{b => 99}`.

What makes it the right starting point:

- No new control flow. Pure expression-level emission.
- No type tracking needed — anonymous objects have no schema.
- Forces us to figure out the property-access dispatch (today `.length`
  on a tuple is hardcoded; we need to extend it to arbitrary field
  names on a map).
- Sets up the syntax patterns that records and `Map<K,V>` will reuse.

The one design question: **keys.** TS keys can be:

- Identifiers (`{ foo: 1 }`) — bare TS identifier
- String literals (`{ "foo": 1 }`, `{ 'foo bar': 1 }`)
- Computed (`{ [keyExpr]: 1 }`) — runtime value
- Numeric (`{ 0: "a" }`)
- Shorthand (`{ foo }` = `{ foo: foo }`)

BEAM map keys can be **any term** — atoms, binaries, numbers, tuples,
even other maps. So we have a choice:

**Option A: keys as atoms.** `{ foo: 1 }` → `#{ foo => 1 }` (BEAM atom
`foo` as key). Fast lookup (atom comparison is one int compare), but
the atom table is a finite resource — BEAM doesn't garbage-collect
atoms, so dynamic key sets could exhaust it.

**Option B: keys as binaries.** `{ foo: 1 }` → `#{ <<"foo">> => 1 }`.
Slower lookup (binary comparison), but no atom-table risk.

**Option C: hybrid.** Static literal keys (the common case) become
atoms; computed keys become whatever their runtime type is.

**Decision: Option A for now.** Idiomatic BEAM uses atoms for stable
keys. The atom-table-exhaustion risk only kicks in if users do
`{ [`field_${i}`]: i }` with unbounded `i`, which is rare. When we add
computed keys we'll revisit and make the atom-vs-binary call at that
point. For static identifier keys, atoms.

Anonymous objects do **not** include computed keys in this step.
Computed keys need a runtime decision and are rare in TS; defer until
someone needs them.

## `Map<K,V>` and `Set<T>` are method-call syntax on top of maps

After anonymous objects work, `Map<K,V>` and `Set<T>` are small.

A TS `new Map<string, number>()` lowers to `#{}` — an empty BEAM map.
A TS `new Set<number>()` lowers to `#{}` (same — sets are maps with
`true` values; the value is uniform so we don't store it explicitly).

The methods lower trivially because BEAM maps already do the work:

| TS                  | BEAM                                                       |
| ------------------- | ---------------------------------------------------------- |
| `m.get(k)`          | `maps:get(K, M, undefined)` (default to avoid badkey crash) |
| `m.set(k, v)`       | `M#{K => V}` (immutable update, returns new map)           |
| `m.has(k)`          | `maps:is_key(K, M)`                                        |
| `m.delete(k)`       | `maps:remove(K, M)`                                        |
| `m.size`            | `maps:size(M)`                                             |
| `s.add(x)`          | `S#{X => true}`                                            |
| `s.has(x)`          | `maps:is_key(X, S)`                                        |
| `s.delete(x)`       | `maps:remove(X, S)`                                        |

Why `Map<K,V>` separately from anonymous objects: TS has both as
distinct constructs, and TS programmers use them differently. Anonymous
`{ name: "x" }` is for "fixed shape." `new Map()` is for "dynamic key
set." We honor that distinction by lowering them to the same BEAM
primitive but with different surface APIs.

One asymmetry: TS `Map` is mutable (`m.set(k, v)` modifies in place).
We can't be — BEAM is immutable. So `m.set(k, v)` returns the new map,
but a `const m` binding doesn't get rebound. Same situation as
`arr.push` — but here we don't reject it. Why?

Because TS users overwhelmingly use `Map.set` for *initialization*
(building up the map), not for in-loop mutation. The pattern is:

```typescript
const m = new Map<string, number>()
m.set("a", 1)
m.set("b", 2)
```

If we silently dropped the return value, the user's map would never
get populated. That's the same silent-bug class we rejected `arr.push`
to avoid.

**Decision: reject in-place `m.set(k, v)` calls** (the user uses the
result implicitly by relying on `m`'s binding to update). Force the
user to either:

- Use anonymous object literals + spread: `const m = {...m, a: 1}` —
  works for fixed-key cases.
- Build the map functionally: `const m = [["a",1], ["b",2]].reduce(...)` —
  works for dynamic.
- Or wait for proper `let` rebinding (Phase 3-ish) to use idiomatic
  mutable-style `let m = m.set("a", 1)`.

Until proper rebinding, **`Map` and `Set` are mostly read-only types**
in TSBeam: you can construct them (from an iterable / array of pairs)
and query them, but not incrementally mutate them. We document this
clearly. Real-world TS code that uses Map this way will compile fine.

This is in scope for this round only if it lands without surprises.
If it's awkward, defer to a later round. Anonymous objects and
interfaces are the must-haves.

## Interfaces are anonymous objects with a schema

`interface User { name: string; age: number }` is a *compile-time*
declaration in TS — it has no runtime existence. But it gives us
information: "anything typed `User` has exactly these fields with
these types."

What we do with that information:

**Option A: ignore it.** Interface = type erasure = nothing changes at
emit time. Objects typed `User` still lower to anonymous BEAM maps.
Field access is `maps:get`. Easy. But: we miss the perf opportunity.

**Option B: track it.** When we see `const u: User = { name: "x",
age: 1 }`, we know the shape. We can emit a BEAM **record** instead of
a map. Record fields are positional indices into a tuple, looked up by
name at compile time. O(1) field access, matches TS's JIT-warm hidden
class speed.

**Decision: Option B.** This is exactly the gap from the principle
discussion — TS programmers expect `obj.field` to be O(1) on
interface-typed objects (because TS hidden classes deliver that),
and BEAM records are how we match it.

The infrastructure isn't trivial:

1. The parser already understands `interface` declarations (TS Compiler
   API gives us them as `InterfaceDeclaration`).
2. We collect interfaces during emit, like we do for module functions.
3. When emitting an object literal whose *contextual type* is an
   interface, we emit a record instance instead of a map.
4. When emitting `obj.field` where `obj` has interface type, we emit
   `element(N, T)` (record fields are tuple slots) instead of
   `maps:get(name, obj)`.
5. We need the TS type checker to tell us "this object literal has
   contextual type X" — that's `TypeChecker.getContextualType(...)`.

Step (5) is the load-bearing part. So far the emitter has avoided
using the type checker — it walks the AST symbolically. To do records
right, we now consult `program.getTypeChecker()` for contextual type
information. That's a real architecture addition: the emitter goes
from "pure AST walker" to "AST walker with type info."

We accept the addition because the alternative — heuristics like
"if the object literal is assigned to a `const` whose annotation is
`User`, treat as record" — is fragile (breaks on returned objects,
function arguments, etc.). Use the type checker.

This also opens the door for future type-aware optimizations and
type-directed lowering (e.g. discriminated unions → pattern matching).
A net architectural improvement.

**Scope reduction:** for this step, interfaces only work for
**top-level interface declarations** referenced directly in type
annotations. Generic interfaces (`interface Box<T>`), interface
extension (`interface A extends B`), and intersection types
(`A & B`) are out of scope. The 80% case for "object types" is plain
flat interfaces with named fields. That's what we deliver.

## What this rules out, and what's still open

Ruled out (won't relitigate):

- ❌ Atom-based keys for everything (would risk atom-table exhaustion
  with dynamic keys; see Option C above — we'll add the hybrid when
  computed keys land)
- ❌ Records by default for all objects (loses the "anonymous" use case
  where the shape isn't known)
- ❌ Mutable `Map.set` semantics (silent footgun for `const m`; reject)
- ❌ Computed keys this round (`{ [keyExpr]: val }`) — defer
- ❌ Generic interfaces (`interface Box<T>`) — defer
- ❌ Interface inheritance / intersection — defer
- ❌ Optional properties (`name?: string`) at the record level — defer

Still open:

- **How to handle objects passed across module boundaries.** If module
  A's `interface User` is at slot positions 1=name, 2=age, but module
  B has a structurally identical `User` with possibly different field
  ordering, do they interop? For now: yes, as long as both modules
  declare the same interface. We're not building a cross-module type
  system; we're using interface schemas as a single-module
  optimization hint.
- **Pretty-printing.** `console.log(user)` on a record produces
  `{user, "alice", 30}` (the tagged-tuple form). On a map it produces
  `#{name => "alice", age => 30}`. Different shapes. Decide when we
  hit it.
- **The `~p` format-string output for nested objects** — same issue we
  already have with strings (chars list quoted). Phase 2 step 4
  (strings as binaries) and step 3 (objects as maps) compose
  cleanly with `~p`; we'll see how it prints when we get there.

## Order within this round

1. Anonymous objects (gets `maps:*` emission infrastructure)
2. Add interfaces + records on top
3. Add `Map<K,V>` and `Set<T>` constructors + methods

Each builds on the previous. We test through after each phase, not at
the end.
